## PROPOSED_CONTRACT · 唯一 after-set

P5 在同一 server slot 為每一實際執行的 release 或 effect statement 核發唯一正 `long requestId`，使用 P5 已有不回繞分配責任。Target 與原因沿 exact P5 actor／level／carrier／target witness，由 P9 port 重驗。Public `DamageInvocation.targetId()` 只作 exact call 內值比對，不用它掃描／補找目標。兩 ID 在 P6 內各自驗證；P5 分配 request namespace 正交於 legacy scope，不能藉數值相等或不等取得權利。Backend release 使用同一 P5 queue 的具名 release event ID，`statementOrdinal=-1`；`on_hit` 的唯一 native damage 使用該 event ID 與 author ordinal `0`。其後的 `CreateSpell` 若合法，仍是下一 ordinal 的 P5 自有 statement、查原 exact closure，無 P6 commit/receipt、無相同 stack 內 child drain。Root 和 child 各一次 closed spawn；`on_create` 空 stack，`on_destroy` 只有 P5 工程觀測。

每次 V0 invocation 固定一份 `EffectCommitPlan`、一個 index 0 primary step、宣告 primary 上限 1、P6 child demand 與 capacity 均 0。沿原 immutable `ActionExecutorRegistry` 的兩條純投影，再走 **按 V0 call 選擇的 closed resolver**，各 binding 與 cap 來自相同 V0 policy 而非 legacy metadata。V0 C descriptor 是 `gramarye:v0_hit_damage`，`damage_hp` 是 INTEGER 1..4，預設 fixture 2；P5 執行 `Math.multiplyExact((long) damageHp, 1000L)`，當次 P6 pure projection 才使用現有內部 action key。只容許 profile code 0 的 P9 native spawn scalar，V0 appearance 由 P8 同次另取 snapshot。僅 root spawn 允許明示 zero 或 server 已捕獲的正 fee，正 fee 預設 1、hard 4，現有 Mana 整數單位。Child spawn 與 damage 固定 0。Damage 每次唯一目標出自合法 claim，閉域 1,000／2,000／3,000／4,000，配置上限內始可接受，預設 fixture 2,000（2 HP）、hard 4,000（4 HP）。入 world 前 P9 驗實際 `SpawnCommit`／`DamageCommit` 與原 exact reserved call 的 ID、scalar shape、target、context 全吻合。其 scalar 不能單獨當 capability。

交易沿同一 `ActionDamageTransactionEngine`（同一現有實例）與唯一 `EffectExecutionEngine` ordered loop。新增 package-private V0 resolver 和 closed call-specific commit outcome 路徑，shared preparation/step/accounting 留在原 owner。推薦在 effect owner 抽出 **內部 outcome** 封閉族供同一步驟 dispatch loop，既有 `EffectStepOutcome` 為 `Confirmed` 原樣 wrapping，V0 增 `V0NativeUnknown`。`Legacy EffectCommitPort` descriptor/return 原樣，經 package-private adapter 投影到上述 outcome；V0 port 的四值可明確區分 APPLIED、已 apply 後失敗、具證未完成與未知。Loop 正常 confirmed branch 仍以既有 attempts、mutation accumulator、traces、finalizer 處理，unknown 在同一位置短路為 V0-only unresolved attempt，絕不進 zero-mutation 判定、compensation、legacy rich result 或 legacy trace。內部可用 package-private 封閉 record 攜已捕獲 ID/attempt 與確認 prefix；PREPARED 與本次 resolver/port/guard 都是 stack local，不為 engine 或 legacy adapter 增加 live fields。Mana debit 和 eligibility 判斷維持單一流程；V0-only unknown bypasses refund/finalize 的 legacy 六種 terminal，原 terminal enum、trace enum、failure enum、port 與 legacy result 都保留原值。不能以 sentinel exception 表示正常 unknown，不能把它偽裝成 `NOT_APPLIED` 或虛構 mutation。此設計的 shared loop 消費者要核對結構上仍只有一個 loop 與一個 native dispatch，並同步以字串硬認 `prepared.commitPort()` 呼叫的行為靜態測試。

### 付款、資格與關閉順序

1. P5 在 owner thread 先驗 `Accepted` work、exact runtime slot/generation/instance/event/target 或 origin／source／deadline／loaded witness、native capacity、P11 W。P6 call wrapper 先由 ENTRY 對 exact actor、命令座標、slot context 做互認並消耗一次 call identity。原 P6 ENTRY→request validation→pure Resolve→immutable plan→PRE_COMMIT 都在 charge 前。Runtime/actor 資格失效時不啟動 debit 或 native。正費不得走 detached 路徑。
2. Prepared plan 通過後，P6 先呼叫 `checkDebit` 驗正費 actor/source，再由 P6 自己的 call-local account 讀 existing Mana availability/餘額，以免為已確定不能開始的付款先打開 native scope。此預檢不代替正式 debit，也不向根 package 暴露帳戶資料。Root wrapper 再以原 W 取得相應 `P11NativeOperationBoundary.OperationScope`，再重驗 actor/phase/source，涵蓋此次 Mana debit 或 native attempt 的真責任。正費在任何 `OperationScope` 開啟後再呼叫同一 `checkDebit`，通過才准封閉交易核心實際 debit。P11 `Fop`、實際 downstream `N/Qctx/Dd/Iw/H` 與 whole R 依原規範，不衍生 V0 的自動 C4a blocker。P6 不取得 P5 slot、W 或 P11 operation handle；root wrapper 和其 adapter 同呼叫持 scope 並 close。Caller 先形成資源一致的 clean failure，再關 P11 scope 並才處理可選 diagnostics／P8。一律沒有跨 tick 的 P6 物件。
3. 正費只以同一 exact actor A 建立 call-scoped account。P11 root package 唯一新增付款讀取為 `Optional<P11ReceiptLedger.Source> P11QualifiedSourceOwner.WorkReservation.paymentSource(ServerPlayer exactA)`，唯一 caller 是 root `V0P6StatementGuard`。判定與取得 proof 同次執行：以 `workRecipient(this, exactA)` 核對原 W 和 canonical input，要求 `recipient.actor == exactA` 且 `canSerialize(recipient)`，並沿原 owner 的 live source 判斷拒 B candidate、constructing、cleanupUnknown、失格或 retired。成功只回當前既有 immutable Source；empty 即拒。單一讀取同時回答 eligibility 和 source 身分，減少一個方法並排除先驗 boolean、後取另一 source 的窗口。在 debit 點同時查原 connection/listener、server roster exact A、PLAY、alive、nonremoved、native permission。V0 account `availability`、`balance` 以 `ManaAttachments.existing(A)` 讀現有合格資料，缺席／unavailable 拒絕，避免在 guard 或零費路徑建立 balance。實際 write 經同一 `ManaAttachments.replace` 和 `ManaTransactionService`；滿額與負餘額演算仍由該 service 控制。零費不接觸 Attachment、不寫 cooldown key、無 PENDING/ARM 義務、現有持久與 sync 不介入。
4. 確定扣款後，P6 最後尚須 BEFORE_STEP guard；它檢查原精確工作與 P9 reservation。未開始 native 的具名預期取消／期限，或有證確定該次 primary spawn 未插入，才可進補償候選。P6 call-local account 在 debit write 前記 exact A 的 `P11ManaMaterial.capture`，正式 write 後立即捕獲新 immutable Mana state identity。Root wrapper 只透過同一 `paymentSource(exactA)` 取得兩次 exact proof，再確認本次 Fop scope、W、exact A body/source incarnation/epoch，且 pre/post debit 的 P11 source version 在同次 write 上由 n 進到 n+1。這是 P11 可守的 package-private observation，採 `body.mana` 與 `P11ManaMaterial.State.isCurrent(A)` exact witness，比對原 actor/account identity。下一步若允許補償，需當前 Mana state 還是該 debit 產物的同一 identity；若 P11 因真 native save 等 advancing version，只能接受仍為原 body/source incarnation 且 original owner 可證完整的同次 lineage。不能以 balance 數字相等代替 exact attachment、以單調版本猜權威、以 refund 重寫原生保存或以 UUID 轉向 B。無其他 native mutation 再入證據、錯誤 source、changed balance、P11 資格失效、已 receipt close 或 UNKNOWN 均不可推定 refund。可在同次正常 detach 後還原只有在原 A 仍 canonical writable、同次原 scope 與既有 Mana refund guard 皆證成；這只是原同次 debit 的 compensation，沒有 detached 正 debit 或第二 payer。
5. `ManaTransactionService.refund` 最多一次。Exact source 不允 refund、Service 拒絕或 invalid receipt 是具名 compensation failure；沿既有 invariant exception 規則出界且不重試。P5 於 fault containment 留最小 scalar「已證無 primary／compensation unresolved or failed」；不能稱已回補。意外 throw（含 debit／refund publication throw）保原物件、已知 native 前綴、未明付款尾段，不做 catch-and-refund。Native callback 中可能進入 logout、death／realm transfer、reload、stop 或本次 native add 移除，需靠 call-local monotonic fact 與 P5 seal 重驗；沒有假定 JVM 跨 owner 原子性。
6. P9 custody OPEN、P6 confirmed apply、既有 formal legacy ARM 三者各自具名。V0 released 生效須 P9 exact OPEN，且該次 P6 confirmed outcome 對得上，`on_create` 才 enqueue；真 confirmed native 已插入但 OPEN 失敗收束為 applied-with-failure、保留指明 applied prefix、關載體，禁止退款。Throw 路徑不產返回的 P6 receipt，adapter/P5 的 fault terminal 可用已捕獲的 native scalar witness 記 `proved applied` 或 `unknown`，並以 `finally`／owner safety 清理；不捕捉後重試，也不把 primary 換成 cleanup 例外。發生 Error 始終不繼續 world 或 optional projection。
