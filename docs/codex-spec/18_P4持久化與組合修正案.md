# P4 持久化、Attachment 與組合修正案

> 狀態：已核准的範圍限定修正案。
>
> 本案只修訂 P4 的 Skill Store persistence、玩家技能 Attachment、submission
> composition、recovery journal、offline roots 與 reconciliation 邊界。在本案明示的
> 範圍內，本案優先於較舊的凍結骨架、P3 scoped amendment、實作總規格與詳細工程步驟；
> P0～P3 以及未被本案明示修訂的規則繼續有效。若其他權威文件尚未同步而形成實質衝突，
> 必須停止受影響工作並回報，不得自行選邊。

## 1. 修訂範圍與既有真相

本案不重寫下列既有責任：

- P3-D Store 的 owner truth、quota counting、CAS、revision allocation 與 reclaim rules。
- P3-B2／P3-B3 的 resolution、payload migration、validation 與 runtime projection。
- `SkillDocument` 作為 revision 內容唯一真相；`ValidatedSkillDefinition` 仍是可重建的
  transient projection。
- Store 最大 retained revision 仍是 latest 與 allocator truth；Attachment pointer 不是。
- `gramarye_skill_definitions` carrier 只承載 P3-D Skill Store 與 P4 recovery journal。
  `RuntimePersistentStore`、Marker／Construct／Schedule 本體與其 persistence schema 不納入
  P4-A～P4-E，也不得偷渡進此 carrier；它們依後續既有功能階段或另行核准的排程實作。

## 2. P4 工程階段

### P4-A1：Raw tree／mixed-family document bridge

- `SkillOwnerId` canonical Codec。
- JSON／NBT／RegistryOps family／context 的唯一判定、bounded raw bytes 與 strict raw Codec。
- `RawTreeEnvelope`、mixed-family current document encode／hydrate、appearance physical mapping
  與 shared logical document bounds。
- 無 Store physical schema、migration、carrier 或 SavedData。

### P4-A2：Store blob format 與 migration-before-restore

- `store_schema_version`、Store／History／Revision physical schema 與三層 Store byte ceilings。
- Store physical migration、logical opaque-token conformance migration、migration-before-hydration、
  current Store snapshot 建構與 P3-D restore orchestration。
- Bounded migration facts、current Store blob encode／load 與 no-partial typed outcomes。
- 無 `saved_data_schema_version`、SavedData outer carrier、journal domain、commit preflight、live
  carrier publication、dirty 或 heap probe。

### P4-A3：Derived Store carrier primitives 與 heap validation

- 只建立純資料／純函式的 immutable hierarchical encoded Store carrier、從 Store snapshot 的
  full rebuild、history／revision replacement builders、checked aggregate byte totals、以既有
  encoded revision carrier 進行 reclaim filtering，以及 prospective Store-only carrier calculations。
- 以 fixed-heap dedicated server 驗證 64 MiB Store ceiling。
- 不擁有 SavedData lifecycle、live carrier publication、dirty、Store commit、journal domain／
  publication、Attachment 或 composition。

### P4-B1：Pure outer carrier／load state

- `saved_data_schema_version`。
- SavedData whole-root 與 inner-carrier strict physical framing。
- Canonical zero-length no-journal sentinel 與 bounded opaque pending blob。
- Exact-field NBT preflight、SavedData carrier migration 與 bounded decompressed carrier input。
- `store_blob` 委派 P4-A2，成功後以 P4-A3 full carrier rebuild 建立 matching Ready
  candidate／typed failure。
- 無 SavedData subclass、world／filesystem／`DimensionDataStorage` cache lifecycle、dirty、
  Attachment、journal domain 或 composition。

### P4-B2：Overworld platform lifecycle

- Primary file path、compressed-size ingress 與 strict single-member gzip。
- Custom one-time load、Ready／Quarantined／Unavailable SavedData adapter、
  `DimensionDataStorage` cache install 與唯一 Overworld lifecycle。
- Live Store／carrier state ownership、save callback、controlled read／pin／reclaim 與 dirty
  mapping。
- Restart 與 fixed-heap load／save Gate。
- 無 Player Attachment、journal entry parsing、Store commit composition、submission facade、offline
  root collection 或 network。

P4-B1 與 P4-B2 皆完成後，P4-B 才完成。

### P4-C：Player Attachment

- P4-C0 只修訂 permanent player skill Attachment 的 totality、bounded raw preservation、
  destructive oversize quarantine、byte coordinate、duplicate capability、generation／no-op、
  editor 與 implementation Gate；不寫 Java。
- P4-C1 建立 physical V0、bounded total serializer、Ready／PreservedRaw／OversizeMarker、
  Draft persistence／migration、exact bounds 與 prebuilt matching Ready carrier；不得註冊
  Attachment 或建立 player lifecycle mutation service。
- P4-C2 建立 Attachment registration、immutable `setData` service、generation transition、
  death／End lifecycle、P4-D controlled transition seam、P4-E bounded root projection、GameTests、
  fixed-heap Gate 與 phase-local gates。
- 無 Store commit composition、journal、offline enumeration 或 network。P4-C1、P4-C2 與 required
  remote memory Gate 全部通過後，P4-C 才完成。

### P4-D：Submission composition

- P4-D0只修訂journal framing、partial availability、policy ownership、composition與memory Gate
  authority，不寫Java。
- P4-D1建立strict journal、single Store authority snapshot、獨立窄Store submission port、prospective
  Store／journal preflight、opaque commit handle、publication與journal roots。
- P4-D2建立authenticated facade、唯一policy provider與SkillId mint consumer、C1～C4 exactly-once
  preparation、Attachment transition及typed composition outcome。
- P4-D3建立bootstrap／login recovery、persisted-readback clear、paired restart及combined fixed-heap Gate。
- 無network、offline enumeration、P4-E root completeness或Store rollback。

### P4-E：Player roots 與 reconciliation

- P4-E0-A／R1／R2／R2R／R2Q 只用於研究、qualification 與裁決；P4-E0-B 只將核准的
  V0 numeric vector、truth selection、heap floor、completeness、reconciliation 與 lifecycle 寫回權威

  online Attachment source 的25-counter applicability、`online > integrated > disk` arbitration、

  publication、exhaustion、E2 invalidation、Complete permit／handoff lease、server removal與restart權威；
  不改25維counters、heap floor、R2Q profile／case plan／evidence，也不寫production code。
  P4-E0-B.5只固定production `SkillRetentionRootAuditService`首次由P4-E2接入、
  `SkillDefinitionStoreService`長期lifecycle ownership與exact-one final instance、
  `SkillSubmissionRecoveryService`作為sole player-login event owner、P4-D recovery→typed outcome→
  same-call-chain E2 continuation、composition-time exact-identity injection、E2 active production wiring
  closure及E3 exact-same-instance reuse；不裁決recovery outcome admissibility、atomic
  reconciliation、Store grouped validation API、P4-C `int` generation、P4-E index `long`
  generation、E2 result或E3 startup／snapshot／reclaim實作。B.5不寫production code。
  P4-E0-B.6只固定qualification-only direct observation的RecoveryOutcome、E2 result、
  invalidation attempt／accepted與E2-bound `setData` attempt／success座標，並受限授權test-armed
  bounded state、closed nominal package transport、條件式per-container FML exact-instance route與
  cross-package local cells；它不寫production／test code，不宣稱locked FML API存在，不改
  E3／R2Q或任何production語意。
  P4-E0-B.7只修正final qualification receipt的deadline／publication authority：H唯一為
  `COMMIT_READY_DEADLINE`，嚴格約束COMMIT_READY與緊鄰link的preinvoke eligibility；符合資格後
  同一supervisor只可直接呼叫一次same-filesystem atomic no-replace link，其normal return可跨H，
  且是唯一成功座標。B.7不實作Candidate12、不執行cold v3、不放寬process strictness或宣稱
  fsync／crash durability；closure後仍須新的read-only technical review。
- P4-E1 建立read-only bounded scanner、online／integrated／disk player source ingress；只有

- P4-E2 只在 P4-D login recovery 後對當下 online player 作一次 immutable latest／equipped

  controlled reclaim 組成在同一 `ServerStartingEvent` logic-thread call chain，並建立生產形狀
  fixed-1,536-MiB Gate。
- V0 overrun 固定為 `INCOMPLETE_AND_CONTINUE`；無 chunk force、offline write、second listener、
  periodic／background sweep、network 或 cross-tick `Complete`。P4-E1／E2／E3 不得合併。

各階段 absence assertion 只適用於該階段；後續階段依本節明示責任逐步加入。

## 3. Raw-family granularity

- `SkillDocument` 不具有單一 raw family invariant。同一 document、同一 node 可同時包含
  JSON 與 NBT raw subtrees；submission 不得只因 mixed family 而拒絕技能。
- Whole-document 或 whole-node 單一 family tag 不足。下列每一個 raw subtree 必須個別保存
  `RawTreeEnvelope`：
  - Trigger `DefinitionEnvelope.payload`；
  - Action `DefinitionEnvelope.payload`；
  - top-level `AppearanceDocument.Unparsed`；
  - 每一個 `AppearanceOverrideDocument.Unparsed`。
- 所有 `DefinitionEnvelope` payload 都必須加 tag，不得依 descriptor 當下是否存在決定。
- Raw subtree 不得跨 JSON／NBT family convert。

### RawTreeEnvelope V0

```text
RawTreeEnvelope {
  family: "json" | "nbt",
  registry_context: boolean,
  compressed_maps: boolean,
  data: byte[]
}
```

合法組合：

```text
json + registry_context=false + compressed_maps=false
json + registry_context=false + compressed_maps=true
json + registry_context=true  + compressed_maps=false
json + registry_context=true  + compressed_maps=true
nbt  + registry_context=false + compressed_maps=false
nbt  + registry_context=true  + compressed_maps=false
```

下列輸入非法：unknown family、NBT 配 `compressed_maps=true`、缺少必要欄位，或 `data`
超過 hard bound。

- `family` 只表示 serialized tree family。
- `RegistryOps` 不是第三種 family。`registry_context` 只表示 load 後需以當下 authoritative
  `HolderLookup.Provider` 重建 `RegistryOps`；Java registry provider identity 不持久化。
- `compressed_maps` 表示 JsonOps parent map compression policy。
- Definition payload 的 `data` 受既有 `MAX_RAW_PAYLOAD_BYTES` 限制；Unparsed appearance
  使用 §7 的 derived-equal `MAX_UNPARSED_APPEARANCE_BYTES`，不得建立平行 magic number。

### JSON data

- UTF-8，無 BOM，且有 byte bound。
- Canonical storage 可移除 whitespace 並採穩定 object key order。
- 必須保留 structural equality、array order，以及 numeric primitive 的 lexical/value contract；
  例如既有 `1.00` representation 不得被未經明示的 canonicalization 破壞。

### NBT data

- 使用鎖定 API 的 uncompressed arbitrary `Tag` bytes。
- 保留 exact Tag type、numeric type、list order 與 primitive arrays。
- 不經 JSON bridge。

## 4. Appearance persistence

Top-level persistent states 固定為：

```text
default | decoded | unparsed
```

Override persistent states 固定為：

```text
none | decoded | unparsed
```

- Top-level `Rejected` save as `default`。
- Override `Rejected` save as `none`／省略。
- Rejected 的 diagnostic、reason 與被拒 raw tree 均不得持久化。
- `Decoded` 使用 typed canonical appearance fields；`Unparsed` 使用其個別
  `RawTreeEnvelope`。
- Unknown appearance fields 仍依 P3-A 的刻意有損 canonical policy 剝除。

## 5. Persistent Store physical schema

### Version axis ownership

| Version axis | Owner |
| --- | --- |
| `saved_data_schema_version` | P4-B SavedData outer carrier |
| `store_schema_version` | P4-A2 Store physical layout |
| `document_encoding` | P4-A2 Revision physical schema |
| `SkillDocument.schema_version` | P3-B1 `SkillMigrationPlan` |
| DefinitionEnvelope payload schema | P3-B2 payload migration |
| `journal_schema_version` | P4-D recovery journal |
| `attachment_schema_version` | P4-C player Attachment outer layout |
| `draft_encoding` | P4-C Draft physical encoding |
| `SkillDraft.draftSchemaVersion` | P4-C Draft logical adjacent migration |

各版本軸只版本化自己所屬的層；它們同時出現在同一持久化階層，不授權某層跨層執行 migration，
也不建立第二份 skill migration plan。P4-A3 不擁有任何 persistent schema version。

### SavedData carrier

Compressed primary `.dat` 解壓後的 V0 whole root 固定為：

```text
unnamed CompoundTag
├─ data: CompoundTag
│  ├─ saved_data_schema_version: IntTag
│  ├─ store_blob: ByteArrayTag
│  └─ pending_attachment_updates_blob: ByteArrayTag
└─ DataVersion: IntTag
```

Whole root 是 unnamed arbitrary-NBT Compound root，exact fields 只有 `data` 與
`DataVersion`。Inner `data` Compound 的 exact fields 只有
`saved_data_schema_version`、`store_blob` 與 `pending_attachment_updates_blob`。兩層的
duplicate／unknown／missing／wrong-tag-type 全部拒絕，field order 無語意。
`DataVersion` 必須存在且為 `IntTag`，但它是 platform-owned metadata，不是
Gramarye migration version。SavedData save callback 只產生 inner `data` Compound；平台負責
whole root 與 `DataVersion`。

#### Canonical no-journal sentinel

`pending_attachment_updates_blob` 欄位必須存在。Zero-length `ByteArrayTag` payload 是
唯一 canonical no-journal representation；missing field 不表示 empty journal，而是
`MalformedSavedDataEnvelope`。

P4-B 不建立 canonical empty Journal V0，不擁有 `journal_schema_version`，不解析
journal entries，也不檢查 entry count、generation 或 pointer semantics。對 non-zero pending
blob，P4-B 只可：

`MAX_PENDING_ATTACHMENT_UPDATES` 仍只由 P4-D journal domain 消費；P4-B 不得為此建立
entry DTO 或 entry-count 邏輯。

- 在 materialization 前驗證 declared length 非負；
- 驗證 raw payload length `<= MAX_PENDING_ATTACHMENT_JOURNAL_ENCODED_BYTES`；
- 建立 defensive immutable copy。

P4-B save 必須逐 byte 保存 pending blob。SavedData outer migration 除明文的欄位
搬移／重新封裝外，不得修改 non-zero bytes。P4-D 才將 zero bytes 解釋為
empty journal state，並將 non-zero bytes 解碼為 versioned journal。Non-zero malformed journal
由 P4-D 分類，不得由 P4-B 誤報為 outer carrier malformed。

P4-D 的 Journal V0 logical schema固定為下列shape；non-zero physical framing、exact fields、
canonical order與strict decode以§16為準：

```text
{
  journal_schema_version: 0,
  entries: [...]
}
```

`store_blob` 是下列結構的 uncompressed NBT bytes：

```text
{
  store_schema_version: 0,
  history_entries: [byte[], ...]
}
```

`HistoryPersistentEnvelope`：

```text
{
  skill_id: UUID,
  owner: UUID,
  revision_entries: [byte[], ...]
}
```

`RevisionPersistentEnvelope`：

```text
{
  revision: int,
  document_encoding: "family_tagged_subtrees_v0",
  document_bytes: byte[]
}
```

Document storage tree 保留 `SkillDocument` logical outer shape：

```text
{
  schema_version,
  skill_id,
  revision,
  nodes,
  appearance
}
```

每個 node 的 trigger／action shell 保留 `type` 與 `schema_version`，`payload` 改為個別
`RawTreeEnvelope`；`appearance_override` 使用 §4 persistent state。

- Store、History、Revision 都以 `List` 保存，不先轉成 `Map`。Duplicate SkillId／revision
  必須原樣保留至 P3-D restore 判斷。
- Canonical save order：SkillId 依 UUID natural order，revision 依 int ascending。
- Route revision 與 document revision 刻意重複，供 restore pairing audit。
- Store schema 與 SkillDocument schema 彼此獨立。
- 不保存 latest cache、quota count、pins、validated projection、`ValidationResult`、Attachment
  pointer 或 reclaim report。
- V0 不新增 checksum。

### SavedData whole-root exact-field NBT preflight

P4-B1 必須在建立 whole-root `CompoundTag` 之前以 schema-aware strict reader 執行
whole root 與 inner `data` 的 exact-field preflight：

- bounded 讀取 tag type、field name、byte-array declared length 與 framing；
- 拒絕 duplicate／unknown／missing／wrong-tag-type，且不依賴 `CompoundTag`
  last-write-wins；
- 先套用 decompressed whole-root、inner carrier、pending blob 與 Store blob 各自的分層
  bound，再解析 nested content；
- 只接受一個 unnamed Compound root，完整 consume decompressed input 並拒絕第二個
  root、padding 或 trailing bytes。

不得先 materialize whole `CompoundTag` 再檢查 duplicate，也不得使用
`NbtAccounter.unlimitedHeap()`。

### Store exact-field NBT preflight

`StorePersistentEnvelope`、`HistoryPersistentEnvelope` 與 `RevisionPersistentEnvelope` 必須在
完整 `CompoundTag` materialization 前執行 schema-aware bounded preflight：

- bounded 讀取 tag type 與 field name，拒絕 duplicate／unknown field，並驗證 required field
  presence 與 exact tag type；
- 驗證 list element type、non-negative raw count、checked arithmetic、declared count 與
  remaining bytes 的相容性、minimum framing 與 nested `ByteArrayTag` length；decoder 不得依
  declared count 預配置巨大 collection，且在 nested parse 前套用 revision／history／Store
  byte ceilings；
- 完整 consume input 並拒絕 trailing bytes；通過後才可使用 finite `NbtAccounter`
  materialize，或由同一 schema-aware decoder直接建立 immutable physical DTO。

不得先轉成 `CompoundTag` 再檢查 duplicate、採 last-write-wins，或使用 `unlimitedHeap()`。
Physical duplicate／unknown／wrong-tag failure 分別歸類為 `MalformedStoreEnvelope`、
`MalformedHistoryEnvelope` 或 `MalformedRevisionEnvelope`。List 中 duplicate SkillId／revision
entry 必須保留至 P3-D restore；此 preflight 不適用於 arbitrary raw NBT payload 或
`RawTreeEnvelope.data`。

Exact-field preflight 的 list raw count 只是 physical／arithmetic sanity check，不得在
P4-A2 重複實作 P3-D Store domain count ceilings。以下四個上限只由
`SkillDefinitionStore.restore` 裁決：

```text
MAX_COMMITTED_SKILLS_PER_OWNER
MAX_COMMITTED_SKILLS_GLOBAL
MAX_RETAINED_REVISIONS_PER_SKILL
MAX_RETAINED_REVISIONS_GLOBAL
```

Physical impossible count／wrong tag／duplicate physical field 是對應的
`MalformedStoreEnvelope`／`MalformedHistoryEnvelope`／`MalformedRevisionEnvelope`，且
restore invocation count 必須為 0。Physical bytes 超過編碼上限則是對應的 P4
encoded-capacity failure，同樣不得呼叫 restore。若 physical encoding 合法但 domain
count 超限，P4 必須保留 list 形狀建立 `SkillDefinitionStoreSnapshot`，呼叫
restore 恰好一次，並映射為 `StoreRestoreRejected(P3-D CapacityExceeded)`。不得新增
P4 平行 count-capacity failure，也不得把 domain overage 分類為 malformed envelope。

## 6. Migration 唯一真相

不得建立第二個 skill migration registry／plan。

### SavedData outer migration

- P4-B1 建立唯一 `SavedDataCarrierMigrationPlan`，以 `saved_data_schema_version`
  提供 adjacent edges、immutable plan 與 exact coverage。Current schema 為 0，production plan
  為唯一 immutable empty plan。
- Plan 只負責 Gramarye inner `data` layout，包含 `store_blob` 與 opaque pending blob
  欄位的明文搬移／封裝；不負責 Store blob internal schema、`SkillDocument`
  schema 或 journal entry schema。
- Outer migration 完成後才把 `store_blob` 委派給 P4-A2 load；Store、History 與
  Revision physical layout 仍只屬 P4-A2。
- Plan 不得解析 pending journal、不得使用 P4-D journal schema，且除明文的
  outer-field 重封裝外，不得修改 non-zero pending bytes。
- Future schema、missing edge、partial result、step `RuntimeException` 與 `Error` 的處理依
  P3-B1 已核准的 adjacent migration 安全原則：partial 拒絕，
  `RuntimeException` 只保存 bounded class name，`Error` 不捕捉。

### Store physical migration

- P4-A2 建立唯一 `StorePersistenceMigrationPlan`，以 `store_schema_version` 提供 adjacent
  edges、immutable plan 與 exact coverage。
- 此 plan 單獨負責 Store／History／Revision／RawTreeEnvelope physical layout；不得建立
  `HistoryMigrationPlan`、`RevisionMigrationPlan` 或其他平行 physical version axis。
- P4-A3 不建立 persistent schema version；P4-D journal migration不併入此 plan。

### Skill schema migration

- 繼續使用 P3-B1 既有且唯一的 `SkillMigrationPlan`。
- 唯一 production provider 固定為 `SkillMigrationPlans.production()` 或符合現有命名風格的
  等價 API；current schema 為 0 時回傳唯一 immutable empty production plan。
- Bootstrap coverage audit 與 P4-A2 opaque migration facade 必須取得同一 production provider；
  Store／document package不得另建 `SkillMigrationPlan.empty()` truth，public caller不得注入 plan。
- Future production steps仍由此 provider持有，且必須在 registry／server bootstrap audit 前
  完成；不允許 runtime hot mutation。
- `SkillMigrationPlan` 的權威輸入永遠是 logical `SkillDocument` outer schema，不是
  P4 physical `RawTreeEnvelope` wrapper，也不是另一份 tokenized physical schema。
- `SkillMigrationStep` 只能處理 `SkillDocument.schema_version`、skill／document outer
  fields，以及 node／document shell 中明文歸屬 skill-level schema 的欄位。
- `DefinitionEnvelope.type`、`DefinitionEnvelope.schema_version`、logical payload root
  與 Unparsed appearance raw slot 都不可由 skill migration 修改。Payload schema
  advancement 仍唯一歸 P3-B2 payload migration。

`SkillMigrationStep` 必須把 Trigger／Action payload 與 Unparsed appearance raw root 當作
opaque slot：不得讀取、遍歷、比較、hash、依其 branch，也不得依賴 raw
family、registry context、compressed-maps state 或 token sentinel 內容。Step 不得移動、
刪除、新增或重複產生這些 raw slot；immutable outer-tree 重建時只可在
原 slot 原樣帶過恰好一次，也不得改寫 token ID／location／context。這是
production contract 與 repository consistency gate，不宣稱能 sandbox 任意惡意 trusted Java
migration code。

第一個及後續每個 production `SkillMigrationStep` 都必須具備 representation-independence
tests：同一 outer shell 搭配 JSON、NBT、RegistryOps payload 與 P4 token view，必須
產生相同 outer output 與 facts，且 opaque slot 不變。目前 production plan 為 empty，
因此沒有既有 step 需修改。

P3-B2 `resolveFromRaw` 仍是正式 raw-ingress pipeline，不是 legacy／test-only API。
P4 load 不呼叫它，因為單一 `DynamicOps` 模型無法表示 mixed-family document；
P4 改由 `OpaqueSkillDocumentMigrationFacade` 將 raw-free logical conformance view 交給相同
`SkillMigrationPlans.production()`。Hydration 完成後才可使用 P3-B2 typed `resolve(...)`，
不重複執行 Reader 或 skill migration。

### Payload migration

- 仍由 P3-B2 resolution 處理。
- P4 load 不得提前執行 descriptor payload migration。

`RawTreeEnvelope` schema 自身的變動屬 Store／storage migration，不屬 skill migration。
目前 production migration steps 為零，因此本契約調整不需要舊資料 migration。

### Player Attachment／Draft migration

P4-C 的三個版本軸與固定 load 順序為：

```text
Attachment outer migration
→ Draft physical encoding dispatch／migration
→ SkillDraft logical adjacent migration
→ family-aware hydration
```

`AttachmentMigrationPlans.production()`、`DraftPersistenceMigrationPlans.production()` 與
`SkillDraftMigrationPlans.production()`（或符合現有命名風格的等價唯一 provider）各自只擁有一個
版本軸。V0 production plan 可為 immutable empty plan，但三者不得合併成同一 version truth。
Draft migration 不得重用 `SkillDocument` migration 或 payload migration，不得在 Attachment load
執行 registry resolution／validation，也不得配置 `SkillRevision`。

### P4-A2 opaque cross-package seams

P4-A2因document／migration package visibility需要，恰好核准兩個public cross-package
facade classes；最小immutable handle／result不計入facade數量，P4-D composition facade也不在
此phase-local計數內：

1. `com.yo1no.gramarye.magic.definition.document.SkillDocumentStorePersistenceFacade`：作為
   `definition.store ↔ definition.document` 的唯一受控 document persistence seam，同時提供
   current document encode 與 always-migrating load 兩條窄路徑。
2. `com.yo1no.gramarye.magic.definition.migration.OpaqueSkillDocumentMigrationFacade`：接收
   完全不含 raw payload bytes 的 immutable encoded tokenized-NBT logical-conformance
   handle；此 handle 是 logical `SkillDocument` outer schema 的 transient representation，不是
   physical Store document或第二份 migration schema truth。Facade 使用
   唯一 production `SkillMigrationPlan`，並重用既有 raw snapshot、schema probe、migrator、
   partial／Ops／exception／schema policies；只回 migrated opaque handle與bounded facts。

#### `SkillDocumentStorePersistenceFacade.encodeCurrent`

概念 API 為 `encodeCurrent(SkillDocument) -> EncodedSkillDocument | typed failure`。它只接受
current-schema immutable `SkillDocument`，委派 P4-A1 既有 package-private
`SkillDocumentPersistenceBridge` current encoder，保留 mixed JSON／NBT family 與
registry／compression context，並執行 A1 logical bounds 與 document byte bound。它回傳
defensive immutable `EncodedSkillDocument`，不公開 physical DTO、`RawTreeEnvelope`、
`JsonElement`／`Tag`／`Dynamic`，不重寫 A1 physical schema，不執行 migration、payload
resolution或validation，且legacy／future `SkillDocument` 不得成功 encode。Public current encode
是 P4-A2 將 live current Store snapshot 建立為 physical bytes 的必要 seam；它不是 load
bypass，也不是 migration bypass。

#### `SkillDocumentStorePersistenceFacade.load`

概念 API 為
`load(EncodedSkillDocument, Optional<HolderLookup.Provider>) -> Loaded SkillDocument/facts | typed failure`。
它必須probe schema：current schema可以0 steps經過唯一production plan，legacy schema必須
走該plan，future schema拒絕。流程為physical document parse → 抽離每個raw subtree至
typed-location side table 並建立logical tokenized conformance view →
`OpaqueSkillDocumentMigrationFacade` → type／schema／token ID／location／context與exactly-once
驗證 → exact reinsertion → P4-A1 package-private current hydrate。它不呼叫
`resolveFromRaw` 或 P3-A Reader，也不提供public
`hydrateCurrent`、`decodeCurrent`、`loadCurrent`或`skipMigration`入口。

#### `EncodedSkillDocument`

Document facade可用最小 public immutable opaque handle `EncodedSkillDocument`（nested public type
或等價窄型別）作為兩條路徑的byte transport。它只保存defensive immutable document
bytes：建立時立即copy，accessor只回copy或受控immutable view，byte count受界，
`toString()`只顯示byte count而不輸出bytes或document。它不保存`RawTreeEnvelope`
objects、Provider／Ops／`Dynamic`／`Tag`、physical field、Store identity或migration facts。
只能由`encodeCurrent` 成功結果產生，或由Store Revision envelope decode以受控
defensive factory建立；該handle不授權caller存取current-only hydrate。

#### Facade responsibility split

- Document persistence facade擁有current encode delegation、physical document parse、logical
  conformance view construction、token extraction／side table、token invariant驗證、raw reinsertion、
  A1 current hydrate delegation與document-level
  failure mapping；不擁有`SkillMigrationPlan`、`RawSkillDocumentSnapshot`、migration step
  orchestration、Store physical format或Store restore。
- Migration facade從唯一production provider取得並消費`SkillMigrationPlan`，並擁有raw
  snapshot、schema probe、migration
  step orchestration、partial／Ops／exception policy與bounded migration facts；不擁有raw bytes、
  A1 current encoder／hydrate、Store physical DTO或Store restore。
- 兩者只交換tokenized immutable outer-document handle與bounded typed result／facts。兩個
  P4-A2 facade都不得接受caller-supplied plan、公開`RawSkillDocumentSnapshot`／`Dynamic`／
  `Tag`，或執行payload migration／registry resolution。Migration facade不執行A1 encode或
  hydration。

Store-facing `EncodedSkillDocument` 是Revision `document_bytes` 的opaque immutable whole-document
carrier，因此必然含持久化raw subtrees，但不提供per-subtree、raw-envelope object或
mutable-tree API。Document／migration之間的immutable tokenized handle／result則在入口立即
defensive-copy encoded bytes，不提供mutable accessor，不含raw subtree bytes，使用bounded
`toString()`，不保存arbitrary／exception
message或stack，且不是persistent schema DTO、不進Store snapshot或disk。除這兩個facade及其
最小immutable handle／result外，不公開其他P3／P4 physical internals。
`EncodedSkillDocument` 與tokenized migration handle必須是不同nominal types，不得共用裸
`byte[]`或同一wrapper；因此編譯期即阻止把含raw的whole-document handle傳入migration
facade。

### Store current encode flow

P4-A2 current Store encode固定為：

```text
SkillDefinitionStore.snapshot()
→ canonical histories／revisions
→ 每份SkillDocument呼叫SkillDocumentStorePersistenceFacade.encodeCurrent(...)
→ RevisionPersistentEnvelope
→ HistoryPersistentEnvelope
→ StorePersistentEnvelope
→ bounded Store blob
```

Store package不得直接呼叫A1 package-private `SkillDocumentPersistenceBridge`，不得複製
document physical encoder，不得用`SkillDocumentWriter`當mixed-family Store serializer，也不得
以`Codec.PASSTHROUGH`或單一`DynamicOps`重建整份mixed document。

### Logical conformance view 與 opaque token contract

P4-A2 skill migration前必須從 physical document 建立 logical `SkillDocument` conformance
view。此 view 保留 skill／document／node outer fields，並對每個 Trigger／Action
`DefinitionEnvelope` 保留 `type` 與 `schema_version`；其 logical `payload` root 以 opaque
token sentinel 取代。Top-level 與 per-node Unparsed appearance 的 logical raw slot 也直接
以 sentinel 取代。Physical `RawTreeEnvelope` 的 `family`、`registry_context`、
`compressed_maps` 與 `data` bytes 均不得進入 migration-visible tree，只能留在
package-private ordered immutable side table。

每個 side-table entry 綁定：

```text
tokenId
typed original location
SerializedTreeContext
exact immutable raw bytes
```

Typed location至少有 `TriggerPayload(nodeIndex)`、`ActionPayload(nodeIndex)`、
`AppearanceOverride(nodeIndex)` 與 `TopAppearance`。Token依 node index ascending的trigger、
action、unparsed override配置，最後配置top-level unparsed appearance；最大數由既有結構
推導為 `3 × MAX_NODES + 1 = 769`，不得新增同義hard ceiling。

Transient NBT sentinel 本身固定為：

```text
{
  "__gramarye_opaque_raw_token_v0": IntTag(tokenId)
}
```

Sentinel只存在migration transient logical view，不持久化，也不攜帶raw family
或context內容。Token ID必須non-negative、unique、bounded；每個token必須保持原
ID、typed location 與 `SerializedTreeContext`，恰出現一次且只位於原 logical raw
slot。Trigger／Action token 同時必須保持所屬 `DefinitionEnvelope.type` 與
`schema_version`。拒絕 relocation、exchange、type／schema rewrite、unknown／missing／
duplicate token、ID／location／context mutation、token-bearing slot 刪除、新增 raw slot，
以及移到另一 node／side／appearance。

未來合法relocation必須先核准per-edge relocation manifest或升級`document_encoding`；V0不得
退化為multiset-only檢查。這是trusted migration code的錯配防護，不宣稱Java sandbox。

Raw bytes全部位於side table，migration-visible tree只含固定小型sentinel；256 KiB raw payload
不等於262,144個migration nodes。Tokenized outer tree仍受既有skill migration depth／node
ceilings，每step輸出仍重新snapshot。Token驗證與exact reinsertion後，P4-A1 hydration必須再
執行真實logical document shared budget；tokenized bounds不取代hydrated bounds。

### Pipeline fact aggregation

既有 immutable `PipelineFactReport` 可 additive提供 bounded `append`／`merge`：左側facts依原
順序先加入，右側隨後加入；共用 `MAX_PIPELINE_FACTS`，超cap即停止保存並設
`truncated=true`。任一source已truncated時結果亦truncated；不deduplicate，也不因truncation
推導其他錯誤。不得公開mutable `PipelineFactCollector`，Store package不得複製cap邏輯。
`STORE_STEP_APPLIED`代表P4 Store physical migration，既有`STEP_APPLIED`與payload fact語意不變。
Facts仍不可持久化、不進SkillDocument／Store、不影響validity，也不保存type ID、raw bytes或文字。

## 7. Exact hard byte ceilings

下列值升格至唯一 `MagicSafetyCeilings` 位置：

```text
MAX_STORE_REVISION_ENTRY_ENCODED_BYTES = 1_114_112
MAX_SKILL_HISTORY_ENCODED_BYTES = 8_388_608
MAX_SKILL_STORE_ENCODED_BYTES = 67_108_864
MAX_STORE_QUARANTINE_ENTRY_BYTES = 1_114_112
MAX_STORE_QUARANTINE_TOTAL_BYTES = 16_777_216
MAX_PENDING_ATTACHMENT_UPDATES = 4_096
MAX_PENDING_ATTACHMENT_JOURNAL_ENCODED_BYTES = 1_048_576
MAX_SKILL_SAVED_DATA_CARRIER_ENCODED_BYTES = 69_206_016
MAX_SKILL_SAVED_DATA_FILE_BYTES = 73_400_320
MAX_UNPARSED_APPEARANCE_BYTES = MAX_RAW_PAYLOAD_BYTES
MAX_PLAYER_DRAFTS = 32
MAX_PLAYER_LATEST_STATES = 256
MAX_PLAYER_EQUIPPED_REFERENCES = 64
MAX_PLAYER_DRAFT_ENTRY_ENCODED_BYTES = 1_114_112
MAX_PLAYER_SKILL_ATTACHMENT_ENCODED_BYTES = 16_777_216
```

- Derived equal limits 必須引用既有常數，不複製 magic number。
- Exact maximum只表示該層admission predicate為inclusive，不表示內層schema或其他hard
  limits亦必然合法；maximum + 1必須在該層內部parse前拒絕。各層適用的
  count ceiling與byte ceiling同時成立；P3-D Store domain count ceilings只由restore執行，
  不屬P4-A2 exact-field preflight。
- Unlimited quota 不能突破任何 technical byte ceiling。
- Encode 使用 bounded／counting output，不依理論最大值預配置巨大 buffer。
- Decode 先檢查 byte-array length，再解析內部 JSON／NBT。
- SavedData compressed file 先檢查檔案大小，再用 bounded `NbtAccounter` 限制解壓後
  carrier。
- Attachment byte bound 是 attachment-tag post-materialization boundary，不冒充 whole-playerdata
  parser bound。
- P4-A3 必須以 dedicated-server heap benchmark 驗證 64 MiB Store 上限；benchmark 失敗時
  停止並提出權威數值修正，不得自行靜默調整。

### Player Attachment V0 byte coordinate

`MAX_PLAYER_SKILL_ATTACHMENT_ENCODED_BYTES = 16_777_216` 計算完整
`gramarye:player_skills` Tag 的 **canonical arbitrary-Tag counting coordinate**。唯一計量方法為：

```text
NbtIo.writeAnyTag(tag, boundedCountingDataOutput)
= one Tag type byte
+ complete Tag payload
```

此座標不含 zero-length root name、任何 root-name framing、
`gramarye:player_skills` attachment key／field framing、outer `neoforge:attachments` Compound、
whole playerdata root、gzip framing或whole compressed playerdata bytes。不得稱為 standalone unnamed
Tag encoding，也不得用 `NbtIo.writeUnnamedTag` admission；後者對非-End Tag會多寫兩個 empty UTF
root-name bytes，會形成第二份尺寸真相。P4-C 不得在 raw 與 marker 路徑混用兩種 writer，也不得以
production `+2` 補償常數模擬另一座標。

```text
writeAnyTag != writeUnnamedTag
writeUnnamedTag(non-End Tag)
= writeAnyTag-equivalent type／payload + 2-byte empty UTF root-name framing
```

Future P4-C1 必須用只保存 `long current` 與 `long maximum` 的 bounded counting `DataOutput`：
exact maximum 合法，觀察到 byte `16_777_217` 立即停止，不保存 partial output bytes；計量前不得
`Tag.copy()`，不得配置等長 second byte array，不得用 SNBT／`toString()` length，不得重編 whole
playerdata，也不得捕捉 `Error`／OOME。P4-A1 的 `writeAnyTag` framing 語意可共用，但會先 copy／
materialize encoded bytes 的 codec 不可直接作此 admission guard。

這是 NeoForge 已 materialize per-attachment Tag 之後的 Gramarye state bound，不限制 Minecraft
第一次 playerdata allocation，不是 playerdata file ingress／whole-root／outer attachments／named-field
wire bound，也不宣稱防止 oversize playerdata OOM。真實 nested attachment field 的 type／UTF field-name
framing屬平台外層，不進本 constant，亦不得另建同義 ceiling。

`MAX_PLAYER_DRAFT_ENTRY_ENCODED_BYTES = 1_114_112` 則只計算 `draft_bytes` `ByteArrayTag`
的 raw payload length，不使用 `writeAnyTag` 座標；兩個 ceiling 不得混用。

### SavedData V0 byte coordinates

`MAX_PENDING_ATTACHMENT_JOURNAL_ENCODED_BYTES = 1_048_576` 計算
`pending_attachment_updates_blob` 的 `ByteArrayTag` raw payload length；不包含 field tag
type、field name 或 four-byte byte-array length prefix。Zero-length payload計為0且是§5唯一canonical
no-journal sentinel。Non-zero payload恰為`NbtIo.writeAnyTag(rootCompound, DataOutput)`的輸出：一個
`CompoundTag` type byte後直接接完整payload，不含root name或zero-length UTF root-name framing。
`NbtIo.writeUnnamedTag`在P4-D journal所有encode／decode路徑均禁止；不得混用座標或以`+2`補償。
Exact maximum只表示outer raw-byte admission合法，不保證V0 canonical journal能生成恰好該長度。

`MAX_SKILL_SAVED_DATA_CARRIER_ENCODED_BYTES = 69_206_016` 計算 inner `data`
`CompoundTag` 的完整 unnamed arbitrary-NBT encoding，包含 root type byte、所有 field
headers、Store／pending blob length prefix 與 payload，以及 `EndTag`。它不是 whole
compressed file 的長度。

`MAX_SKILL_SAVED_DATA_FILE_BYTES = 73_400_320` 計算 primary `.dat` 的完整
compressed file length，包含 gzip framing 與 compressed payload 的全部 bytes。

V0 whole decompressed root 相比完整 inner carrier 固定增加 26 bytes，因此：

```text
MAX_WHOLE_DECOMPRESSED_ROOT_BYTES
= 69_206_042
= MAX_SKILL_SAVED_DATA_CARRIER_ENCODED_BYTES + 26
```

26 bytes 來自 outer root framing、`data` field framing、embedded inner Compound 不重複其
standalone root type，`DataVersion` field 與 int payload，以及 outer `EndTag`。這是 V0
derived framing value，不新增 `MagicSafetyCeilings` constant。

P4-B0 核准的 V0 whole-root finite `NbtAccounter` allocation quota 為
`69_206_405`。實作必須以 golden tests 同時證明 inner-carrier framing、whole-root
`+26` 與 finite quota 能接受合法 exact fixture。若任一實測不符，必須停止
P4-B，不使用 `unlimitedHeap()`，不自行修改 ceiling 或 quota，而是提出
後續權威修訂。

Capacity guard 的分層順序為：

```text
compressed primary file size
→ decompressed whole-root framing／bound
→ inner carrier encoded bound
→ pending blob raw payload bound
→ store_blob 委派 P4-A2 Store bound
```

某層 exact maximum 合法只代表通過該層 guard，不表示 nested content 必然合法。
Failure 必須使用實際失敗層分類，不得一律報 whole-carrier capacity。

`MAX_STORE_QUARANTINE_ENTRY_BYTES` 與 `MAX_STORE_QUARANTINE_TOTAL_BYTES` 在
P4-B 沒有核准 consumer，因為 Quarantined state 不自動複製 raw fragments。P4-B
不得為了消耗這兩個常數而建立 raw-copy storage，也不得在未有正式 consumer
前將其加入 Java。第一個 consumer 留待 operator-assisted recovery／quarantine
export 設計。權威數值保留不表示 P4-B 已實作 quarantine storage。

### P4-B fixed-heap Gate

P4-A3 fixed-heap Gate 不能取代 P4-B load／save Gate。P4-B2 完成前必須
在 NeoForge dedicated server 以下列固定參數驗證 full-size path：

```text
-Xms512m
-Xmx1024m
-XX:+ExitOnOutOfMemoryError
```

Workload 必須包含 actual Store carrier `>= 63 MiB`、strict gzip file ingress、
whole-root／inner-carrier decode、P4-A2 load／restore、P4-A3 rebuild、Ready installation、
save callback Store-size copy、可觀測的 platform whole-root deep-copy path、dirty／save
scheduling 與 restart round-trip，且無 OOME／timeout。

若 1 GiB 下失敗，必須停止 P4-B；不得降低 workload、跳過 deep copy、移除 CI
Gate 或靜默改值，而應先修訂 byte ceiling、memory representation 或 minimum heap
requirement。

### P4-C fixed-heap Gate

P4-C 完成前必須以 dedicated server 固定驗證：

```text
-Xms512m
-Xmx1024m
-XX:+ExitOnOutOfMemoryError
```

Workload 至少包含 exact 16 MiB malformed materialized Tag load、bounded count、PreservedRaw
建立、normal player save、restart 仍 PreservedRaw、death／respawn 與 End return write／read copy，
以及 maximum + 1 路徑不複製 raw、建立 bounded marker、save／restart 仍 OversizeMarker。若 1 GiB
下發生 OOME／timeout 或 lifecycle failure，停止 P4-C；不得縮小 fixture 或提高 heap 規避契約，
而應先正式修訂 ceiling 或 quarantine representation。

### Revision V0 outer ceiling

`MAX_STORE_REVISION_ENTRY_ENCODED_BYTES = 1_114_112` 是inclusive physical outer-envelope
admission ceiling，不保證V0 canonical schema能產生恰好同長度的成功文件。V0 framing固定為：

```text
revision encoded size = 85 bytes wrapper + document_bytes.length
```

因此 `MAX_SKILL_DOCUMENT_BYTES = 1_048_576` 時，目前最大完整合法V0 revision為
`1_048_661` bytes。P4-A2測試必須分開證明：

1. Outer長度恰為`1_114_112`時，不得只因revision outer length回
   `RevisionBlobEncodedCapacityExceeded`。
2. Outer長度為`1_114_113`時，必須在內部parse前回revision outer capacity failure。
3. 以最大合法document建立的V0 revision完整encode／decode成功，golden framing為
   `1_048_661 = 85 + 1_048_576` bytes。
4. Outer恰為`1_114_112`但inner document超限時，先通過revision outer guard，再回document
   capacity failure；不得誤報revision outer capacity failure，也不得成功hydrate。

若實作所得V0 fixed framing不是85 bytes，必須停止P4-A2並回報physical schema差異，不得自行
修改ceiling數值或測試期待。

## 8. Migration-before-restore

正式 load 順序：

```text
P4-B2 bounded primary-file ingress + strict single-member gzip
→ P4-B1 strict whole-root／inner-carrier decode
→ P4-B1 SavedData outer-carrier migration
→ store_blob
→ P4-A2 Store physical migration
→ per-history／revision length validation
→ per-document logical conformance view + opaque-token SkillMigrationPlan
→ type／schema／token／location／context／exactly-once validation
→ exact raw reinsertion
→ P4-A1 family-aware raw hydration
→ current SkillDefinitionStoreSnapshot
→ SkillDefinitionStore.restore
→ P4-A3 full carrier rebuild
→ matching Ready candidate
```

- Migration 必須先於 restore。Restore 不呼叫 migration，也不猜 legacy format。
- Payload migration 不在 P4 load 執行。
- 任一 revision migration／decode 失敗使整個 Store fail closed，不建立 partial Store。
- 原始 bytes、migration intermediate 與 domain Store 均不得原地修改。
- Migration facts 不持久化。
- 只有 outer migration、decode、P4-A2 load／restore 與 P4-A3 carrier rebuild 全部
  成功，且 Store／carrier pairing 成立後，才可建立 Ready candidate。Failure 資料
  不得 canonical rewrite，不得安裝 partial 或 empty Store。
- Outcome 必須區分 `StoreEnvelopeMigrationFailed`、`DocumentMigrationFailed`、
  `DocumentDecodeFailed`、`StoreRestoreRejected` 與 `Quarantined`。
- P4-A2 load回total typed result；只有P4-B在處理existing persisted file時，才把失敗的完整
  load映射成Quarantined lifecycle state。

四類測試必須各自存在，不得以單一 corruption test 取代：

```text
old schema
→ migration
→ current typed snapshot
→ restore success

same old document without migration
→ direct restore
→ UnsupportedDocumentSchema

missing migration edge／migration exception
→ migration failure
→ restore invocation count = 0

migration success + current snapshot domain corruption
→ restore typed rejection
→ not migration failure
```

## 9. SkillOwnerId Codec

- P4-A1 additive 新增唯一 canonical Codec：`SkillOwnerId ↔ UUID`。
- 必須重用 `SkillId` 目前使用的相同 UUID syntax helper 與 representation。
- 不建立 String owner domain ID、`PlayerId` 平行 wrapper、`StreamCodec` 或 player existence

- Codec 只驗 syntax，不判斷 owner 是否存在。

## 10. Derived encoded carrier 與 persistence preflight

P4-A3只建立pure immutable carrier primitives：從current Store snapshot full rebuild、
history／revision carrier replacement、checked aggregate byte totals、以既有encoded revision
entries進行reclaim filtering，以及prospective Store-only carrier calculations。P4-A3不呼叫
`Store.commit`、不持有live lifecycle、不發布carrier、不dirty，也不建立journal domain。

P4-B lifecycle 的 internal state 固定為：

```text
SkillSavedDataState
├─ Ready
├─ Quarantined
└─ Unavailable
```

Ready 同時持有：

```text
SkillDefinitionStore domain truth
matching immutable encoded carrier
immutable opaque pending blob
rewriteRequired
```

Encoded carrier 可由 Store snapshot 重建，是 derived representation，不是第二 domain truth；
不得提供一般玩法查詢，只供 bounded save callback。

P4-B使用P4-A3 primitives持有與發布live carrier；save callback只讀預建carrier，P4-B不得
重新實作Store／History／Revision encoding。

Ready 建立前必須完成：

```text
outer migration
→ P4-A2 complete load／restore
→ P4-A3 full carrier rebuild
→ Store／carrier match
```

`rewriteRequired` 固定為下列任一條件成立：

```text
outer SavedData migration applied
OR P4-A2 Store／document migration applied
OR source Store blob != rebuilt canonical A3 Store blob
```

Migration facts 可能 truncated，不得由 facts 推導 `rewriteRequired`。Current-schema
source Store blob 即使 noncanonical，只要 domain load 成功仍可建立 Ready，但
`rewriteRequired=true`。可為 A3 carrier 新增 package-private 窄 seam
`matchesStoreBlob(...)`；它不得回傳 raw array、不得產生第三份 Store-size copy，
只比較完整 bytes 並不修改 carrier。

Quarantined 只表示 load-time persistent corruption 或 unreadable input。它不保存 empty
Store、raw file bytes 或 broken whole carrier，不 dirty、不 save；controlled API 回傳 typed
subsystem unavailable。初版不允許 in-place recovery，operator 修復後需 restart。

Unavailable 表示 runtime Store／carrier pairing invariant failure，例如 reclaim 後
`filterAfterReclaim` 的不可能失敗防線被觸發。它不等於 load-time Quarantined，
不 rollback Store，不保存／使用 stale carrier 作 save，不 dirty、不 save，controlled
API 回傳 typed subsystem unavailable，並需 operator／restart。

Quarantined 與 Unavailable 必須防禦性地保持 `dirty=false`。Ready 轉成
Unavailable 時必須清除任何尚未排程的 dirty flag，並使 adapter 進入
non-saving state，不得讓後續 callback 輸出舊 carrier。若鎖定平台 API 無法安全
保證這些條件，必須停止 P4-B2。

P4-D commit preflight 在 live Store mutation 前完成：

1. 調用P4-A3 pure builder計算prospective Store carrier replacement。
2. 建立 prospective pending journal replacement。
3. 檢查 revision／history／store／journal／carrier 全部 byte bounds。
4. 完成所有一般可失敗工作。

Store typed failure 時丟棄 prospective carrier delta、不 dirty。Store commit 成功後才發布預建
carrier／journal replacement 並 mark dirty；commit 後不得首次執行一般 Codec。P4 不得為此重寫
owner／quota／CAS 裁決，carrier delta 只在 domain Store 回 `Committed` 後採用。

P4-E 擁有 root collection／completeness 與 reclaim composition；P4-B 只擁有對
caller-provided `SkillRetentionRootSnapshot` 的 reclaim publication：

- `Rejected`：state／carrier 不變，不 dirty。
- `Completed`, reclaimed = 0：state／carrier 不變，不 dirty。
- `Completed`, reclaimed > 0：immediate post-reclaim snapshot → P4-A3
  `filterAfterReclaim` → publish matching new Ready state → set dirty。Carrier publication 必須
  先於 dirty，且不在 Store mutation 前 dirty。

Reclaim filtering 只移除既有 encoded revision entries，不重新跨 family encode raw
documents。若 filter 拋出 adapter invariant failure，不使用舊 carrier、不 rollback Store、
不自動 full re-encode；立即轉入 Unavailable、清除 dirty 並 non-saving。此情況
不稱為 Quarantined，`Error`／OOME 不捕捉。

P4-B controlled adapter API 不得公開裸 `SkillDefinitionStore`、
`EncodedSkillStoreCarrier` 或 SavedData state。本階段只核准 `find`、
`latestReference`、`ownerOf`、`committedSkillCount`、`pin` 與 `reclaim`的
typed controlled operations；API 必須區分 available-but-not-found 與 subsystem-unavailable。
P4-B 不公開 direct Store commit，P4-D mutation seam 留待 journal schema 定案，不得
提前公開 carrier。

## 11. SavedData 安全 load 與唯一 lifecycle

- Stable name 固定為 `gramarye_skill_definitions`。
- 唯一位置是 Overworld data storage；非 Overworld 維度取得同一 Overworld adapter。
- 不使用 static world singleton。
- NeoForge 標準 fail-open `computeIfAbsent` 不得作為技能 Store 的直接 deserializer 入口。

### Unique Overworld cache lifecycle

Bootstrap event 固定為 `ServerStartingEvent`；此時 Overworld 已建立、registries 可用，
`DimensionDataStorage` 可用。安裝流程固定為：

```text
server.overworld()
→ custom bounded primary load
→ Ready／Quarantined SavedData exact instance
→ overworld.getDataStorage().set("gramarye_skill_definitions", instance)
```

每個 `MinecraftServer` instance 只可 install 一次；repeated install 是 programming
invariant violation。Normal load failure 也必須 install Quarantined，install 後才允許
任何 Gramarye accessor。Accessor 不得在 cache miss 時呼叫 `computeIfAbsent`。Nether／
End caller 必須委派 Overworld instance，reload 不重建 Store，dedicated／integrated
語意相同，不得跨 server 共用 static state。

P4-B 不得使用 `readTagFromDisk`、direct fail-open `computeIfAbsent`、reflection
存取 cache，或 bounded pre-read 後再讓平台重讀檔案。

### Primary file ingress

Primary path 固定為：

```text
<world>/data/gramarye_skill_definitions.dat
```

`NoSuchFileException` 或明確不存在才表示 absent；建立 empty Ready Store、matching
empty carrier，初始不 dirty。Primary 存在但 unreadable／invalid 時建立
Quarantined，不建立 empty Store、不 dirty、不覆寫。Primary valid 時只使用
primary。

File ingress 必須：

1. 以 `NOFOLLOW_LINKS` 讀取 attributes，並要求 regular non-symlink file。
2. Open 前檢查 complete compressed-file size bound。
3. 以 `READ` 與 `NOFOLLOW_LINKS` 開啟同一 channel，再次確認 channel size。
4. Replacement／race 異常作 unreadable 處理。
5. 由同一 bounded stream 執行 strict gzip、whole-root preflight 與 §8 pipeline。

不使用 `Files.readAllBytes`，不刪除／rename／修改 raw primary。

### Strict gzip 與 stream EOF

Primary `.dat` 必須正好包含一個 gzip member；第一個 member 結束後必須
立即到達 underlying compressed EOF。第二個 gzip member、任意 trailing garbage、
trailing zero padding 或 member 後任何額外 compressed byte 全部拒絕，不得將
concatenated gzip 視為合法。

Decompressed stream 也必須正好包含一個 unnamed Compound root並立即到達
decompressed EOF；root 後 trailing NBT bytes、第二個 root 或任意 padding 全部
拒絕。Canonical save 只產生一個 gzip member、一個 whole root，且無
compressed／decompressed trailing bytes。

P4-B2 不得依賴會吞掉 trailing data 的便利 API 作完整 reader。若鎖定
Commons Compress／stream API 無法可靠證明 first member consumed 且 underlying
compressed EOF，必須停止 P4-B2，不得放寬為「reader 成功即合法」。

### `.dat_old` policy

`.dat_old` 不自動讀取、不自動提升、不自動刪除，也不作 fallback truth：

```text
primary absent + old present
→ primary absent／new empty Ready

primary invalid + old valid
→ Quarantined

primary valid + old arbitrary
→ primary 勝出
```

`.dat_old` 只供 operator-assisted recovery；failure object 不得保存任意 filesystem
path。Quarantined 允許 dedicated server 繼續運作，但 Gramarye skill data
subsystem 不可提交、commit 或 reclaim；原檔保留且不靜默 reset。

## 12. Save callback 與 dirty matrix

Ready 保存 immutable logical prebuilt save state：Store domain truth、matching
`EncodedSkillStoreCarrier`、immutable pending bytes 與 `rewriteRequired`；不以 mutable
`CompoundTag` 或 whole-root encoded bytes 作 truth。

SavedData save callback 只允許 Ready state，且只可：

1. 建立固定三欄 inner `data` Compound。
2. Copy 預建 Store carrier bytes。
3. Copy opaque pending bytes。
4. 寫入 current `saved_data_schema_version`。
5. 回傳 inner Compound，交由 platform 建立 whole root／`DataVersion` 與排程 async
   write。

Callback 不得第一次執行一般 Codec，snapshot Store、encode document／Store、rebuild
carrier、執行 migration／reclaim、解析 journal、查詢 Store mutation、修改 Attachment
或第一次做一般 capacity admission。

若 Quarantined／Unavailable 意外進入 callback，必須在修改 output tag 前 fail
fast，不輸出 empty Store、stale carrier 或 new-world default。P4-B2 不得引入
未核准的 lock model；若無法以既定 logic-thread confinement 保證 state／callback
一致性，必須停止並先修訂權威契約。

NeoForge async disk write 沒有成功 acknowledgement，因此 public 語意只能承諾：

```text
in-memory domain committed + persistence scheduled
```

不得宣稱 fsync durable、disk write 成功，或 Attachment 與 Store 已 durably atomic。

Dirty matrix 固定為：

| 事件 | Store SavedData dirty |
| --- | --- |
| Primary absent → empty Ready | 否 |
| Current canonical input → Ready | 否 |
| Outer／Store／document migration 成功 → Ready | 是，Ready publication 後 rewrite required |
| Current 但 noncanonical Store blob → Ready | 是，Ready publication 後 rewrite required |
| Store `Committed` + journal published | 是 |
| Store typed failure | 否 |
| pin／close | 否 |
| reclaim `Rejected` | 否 |
| reclaim `Completed`, reclaimed = 0 | 否 |
| reclaim `Completed`, reclaimed > 0 | 是，matching carrier publication 後 |
| snapshot／read | 否 |
| journal 新增／更新／清除 | 是 |
| reconciliation 只改 Attachment | 否 |
| reconciliation 改 journal | 是 |
| migration／decode／restore failure | 否 |
| Quarantined | 否 |
| Unavailable | 否，non-saving |
| Save callback | 不自行新增 dirty |
| Attachment schema migration | immutable replacement `setData` |

## 13. Player Attachment schema

建立獨立永久 Attachment：`gramarye:player_skills`。不得與 mana／cooldown 等不同死亡政策
資料混用。Owner 不持久化，只由 authenticated player UUID 導出 `SkillOwnerId`；client 不是 truth，
Attachment 不得配置 revision 或覆蓋 Store owner／latest，也不自動 sync。

### Totality boundary

Custom serializer 必須使用 `IAttachmentSerializer<Tag, PlayerSkillAttachmentState>` 或等價的
`Tag`-generic total seam。Totality 承諾只從以下三個條件都成立後開始：

```text
NeoForge 已成功 materialize playerdata
AND outer neoforge:attachments 是 CompoundTag
AND gramarye:player_skills 的 non-null Tag 已交給 custom serializer body
```

在此邊界內，任意 non-null Tag 都必須回 non-null Ready 或 Quarantined。預期 data failure 不得
throw、回 `null`、回 empty Ready 或 partial Ready。Whole playerdata gzip／NBT無法 materialize、outer
attachments wrong type、player root／outer duplicate fields 已被平台消解，或 attachment key 在
serializer body 前被平台忽略，都不在此 totality 保證內，文件與 API 不得宣稱可觀察或修復。
以 `CompoundTag` 作 serializer generic 會讓 wrong-root Tag 在 synthetic bridge cast 失敗並被平台
skip，因此不得採用。

### State model and quarantine policy

```text
PlayerSkillAttachmentState
├─ Ready
└─ Quarantined
   ├─ PreservedRaw
   └─ OversizeMarker
```

Ready 保存 immutable Draft／latest／equipped／editor semantic state及其 matching prebuilt current
carrier；不得保存 owner、Player／ServerPlayer、Store、journal、mutable collection、validation report
或 profile object。Missing attachment key 才由 default supplier 建立 empty Ready。

`PreservedRaw` 只適用於 `writeAnyTag` bounded counting 完整成功且 count
`<= MAX_PLAYER_SKILL_ATTACHMENT_ENCODED_BYTES` 的 malformed existing Tag。固定順序為：

```text
count
→ bound accepted
→ deep-copy materialized Tag
→ PreservedRaw(bounded machine failure, immutable raw snapshot)
```

正常 save 回傳 fresh `raw.copy()`。保證只涵蓋 materialized logical NBT tree structural
preservation；不保證原 compressed bytes、Compound field order、duplicate field occurrences、whole
playerdata byte identity或gzip metadata。Raw Tag 是 Quarantined persistence state，不是 failure
metadata，也不是 Ready 的第二份 truth；不得保存平台傳入 mutable alias，returned Tag mutation不得
反向影響 state。

`OversizeMarker` 適用於同一 `writeAnyTag` counter 觀察到
`MAX_PLAYER_SKILL_ATTACHMENT_ENCODED_BYTES + 1 = 16_777_217`。立即停止 counting，不複製原 raw，
不保存 partial／prefix bytes、hash、exception message或stack；只保存 fixed machine code、
`observedAtLeast = 16_777_217` 與 `maximum = 16_777_216`。正常 save 回 fresh canonical marker。
這是明示的 destructive quarantine：下一次正常 player save 可能以 marker 取代原 oversize malformed
representation，不保證原 raw／key bytes或永久 `.dat_old` recovery；不得稱為 lossless preservation，
也不得稱為 silent data loss。Operator diagnostics 必須明示 replacement，restart 必須仍為
`Quarantined.OversizeMarker`，不得變成 missing 或 empty Ready。此例外只適用於違反 complete Attachment outer
hard bound、未被 admit 的輸入；不放寬任何 in-bound unknown Definition payload round-trip 契約。

Canonical oversize quarantine marker 固定為：

```text
CompoundTag {
  "__gramarye_attachment_quarantine_v0": CompoundTag {
    "schema_version": IntTag(0),
    "code": StringTag("encoded_capacity_exceeded"),
    "observed_at_least": LongTag(16_777_217),
    "maximum": LongTag(16_777_216)
  }
}
```

Outer marker exact 只有一個 field，nested marker exact 只有上述四個 fields；unknown／missing／wrong
type、其他 code 或 metadata value 不得猜測修復，而是按一般 in-bound malformed Tag 建立
PreservedRaw。Marker 自身以同一 `writeAnyTag` coordinate 驗證、遠低於 cap、deterministic write，
每次write回fresh Tag且returned marker mutation不影響state；它不是 unnamed-root document、不保存
root-name framing、player／owner／path，也不是 Ready schema的追加欄位。未來增加 destructive
quarantine code 必須正式 schema migration，不能接受任意字串。

P4-C V0 不建立 per-player sidecar、world-level Attachment quarantine Store、raw export directory、
whole playerdata copy、save-cancellation registry、retry queue、login-denial protocol、mixin或access
transformer，也不阻止整份 playerdata save。未來若產品不接受 oversize raw 被 marker 取代，P4-C
implementation Gate 保持關閉，必須由新修正案定義另一持久化位置或 file-level quarantine 的 truth
ownership、hard bounds、lifecycle、reconciliation、cleanup 與 operator tooling。

### Ready V0

V0：

```text
CompoundTag {
  attachment_schema_version: IntTag(0),
  drafts: ListTag<CompoundTag> [
    CompoundTag {
      skill_id: IntArrayTag[4],
      draft_encoding: StringTag("family_tagged_subtrees_v0"),
      draft_bytes: ByteArrayTag
    }
  ],
  latest_states: ListTag<CompoundTag> [
    CompoundTag {
      skill_id: IntArrayTag[4],
      mutation_generation: IntTag,
      pointer?: CompoundTag {
        skill_id: StringTag(canonical lowercase UUID),
        revision: IntTag(non-negative)
      }
    }
  ],
  equipped_slots: ListTag<CompoundTag> [
    CompoundTag {
      slot: IntTag,
      reference: CompoundTag {
        skill_id: StringTag(canonical lowercase UUID),
        revision: IntTag(non-negative)
      }
    }
  ],
  editor: CompoundTag {
    selected_draft?: IntArrayTag[4],
    selected_node_index?: IntTag
  }
}
```

Every Compound above has exactly the listed fields；`?`只表示field absence，wrong type、unknown或
missing required field均是malformed。Route／editor SkillId使用`SkillId.CODEC`在`NbtOps`下的
`IntArrayTag[4]`；pointer／reference重用現有`SkillReference.CODEC`的exact Compound shape，不新增
String UUID平行route format。Pointer存在時其reference SkillId必須與latest route相同；Draft entry
route也必須與`draft_bytes`內的logical SkillId相同，不得自行修正。

三個List在non-empty時declared element type必須是`CompoundTag`且count > 0。鎖定Minecraft
`ListTag.write`對canonical empty list固定輸出element type `EndTag`（0）與count 0；因此empty Ready
的三個List必須使用該canonical representation。Materialized empty List的pre-count noncanonical
declared element-type byte不屬logical structure：`writeAnyTag` counting可依鎖定writer將它正規化為0，
V0以count 0的logical empty狀態admit並在canonical output寫type 0。PreservedRaw的structural guarantee
明確不包含此無element的metadata byte；tests不得以`getElementType()`或physical bytes冒充logical
equality。若未來要求保留它，必須另修authority，不能在C1改用`writeUnnamedTag`或pre-copy規避。

Ready outer exact fields與tag types維持上述 V0。`drafts`、`latest_states`、`equipped_slots` 必須以
`ListTag<CompoundTag>` 作 raw decode input，保留 input order直到完整 validation；不得先 Map 化。
可以且必須拒絕 Draft SkillId、latest SkillId與equipped slot duplicate，以及由 P4-C strict
`draft_bytes` parser看到的duplicate fields。Platform materialization已透過 `map.put` 對 Attachment
root、nested materialized entry Compound、outer `neoforge:attachments`與player root的同名 field
採 last-write-wins；serializer不能偵測已消失的 occurrences，文件不得宣稱 wire-level Compound
duplicate rejection。Canonical write依 Draft／latest SkillId order與equipped slot order輸出。

Decode precedence 固定為：

```text
writeAnyTag bounded total count
→ exact oversize quarantine marker recognition
→ Ready V0 outer migration／strict decode
→ in-bound malformed PreservedRaw
```

一旦 total count 觀察 maximum + 1，直接建立 OversizeMarker，不進 marker 或 Ready decode。Quarantine
marker不得進 Ready migration。Total Attachment cap 優先於個別 Draft cap；32份 Draft不表示每份可
同時達到個別最大值。Draft read facts／`ValidationResult` 不持久化。

### Latest generation and editor policy

`mutationGeneration` 的 Java／domain type 固定為 `int`，persistent type固定為 `IntTag`，合法範圍
`0..Integer.MAX_VALUE`。`LongTag` 即使值可放入 int 也拒絕。Latest entry沒有 `pointer` field表示
empty pointer；route entry完全 absent表示 implicit `(empty pointer, generation 0)`；explicit empty
pointer且generation > 0必須保存。Pointer存在時其 SkillId必須與entry route相同，但decode不查Store
existence。

Same target pointer一律是no-op，包括same present、empty → empty、implicit absent → empty，以及
MAX generation上的same pointer。No-op不增加generation、不呼叫`setData`、不建立P4-D journal。
Changed transition才由P4-C唯一checked helper執行：current `< Integer.MAX_VALUE`時target = current + 1；
current為MAX時typed fail closed，不wrap、saturate、reset或reuse。P4-D不得另寫successor arithmetic。

Editor `selected_node_index` wrong tag type、negative或 `>= MAX_NODES` 是hard-invalid，使整個Ready
decode失敗並依total count形成PreservedRaw或OversizeMarker。以下是structurally valid stale metadata，
必須原樣保留且不得silent clear：selected Draft不在Draft list、index存在但selected Draft缺失、index
超過目前selected Draft node count。它們是inactive UI state，不阻止其他資料載入、不進retention
roots；後續editor service可將其呈現為stale／inactive。

### Attachment lifecycle

```text
missing key → default empty Ready
in-bound malformed key → PreservedRaw → future save raw.copy()
oversize malformed key → OversizeMarker → future save canonical marker
canonical marker restart → OversizeMarker
```

兩種Quarantined均由custom read回傳non-null state並安裝於Attachment map，`hasData`保持true；不得
藉由read／write `null`或exception省略key。

永久 player skill Attachment使用custom serialize + `copyOnDeath()`。NeoForge default copy由
serializer write(old) → serializer read(new holder, fresh Tag)重建，因此Ready經canonical Tag、
PreservedRaw經fresh raw copy、OversizeMarker經fresh marker跨death／respawn／End；不共享mutable Tag，
不註冊manual clone copy，keepInventory不改此政策，End return不得double-copy。Normal dimension
transfer不另建state，P4-C不建立sync handler、network payload或client mirror。

## 14. Submission composition

### P4-D phase split

P4-D固定拆為四個phase，不能把physical journal、normal submission及recovery塞入同一輪實作：

- P4-D0只修改既有authoritative Markdown與architecture ledger，鎖定journal framing、partial
  availability、policy ownership、composition boundary與combined fixed-heap obligation；不寫Java。
- P4-D1建立journal physical model／migration／operational state、single Store authority snapshot、
  獨立窄Store submission port、opaque prepared commit handle、journal roots，以及Store＋journal
  publication；不建立submission facade或event listener。
- P4-D2建立authenticated normal submission、唯一policy provider、Draft creation／SkillId mint
  adapter、P3-C exactly-once composition、prepared Attachment transition與composition outcome；不建立
  recovery listener。
- P4-D3建立journal bootstrap、login recovery、persisted-readback clear、paired crash／restart probes、
  combined fixed-heap Gate、Gradle／CI及final phase gates。

P4-D只有D1、D2、D3及required remote memory Gate全部通過才完成；P4-E不得提前開始。

### Authenticated input, owner and Draft authority

P4-D facade位於`com.yo1no.gramarye.magic.definition.submission`。Public submit入口只接受
authenticated `ServerPlayer`與caller-known `SkillId`，並重用package-private C1～C4 stages；不得接受
client或caller聲稱的owner、authorization、quota、`ValidationContext`、revision、Store state、Draft
body、plan、base revision、Attachment generation或expected latest。

Owner固定由authenticated player UUID導出。Draft只從該player的Ready
`gramarye:player_skills` Attachment取得；Attachment Quarantined／Unavailable或Draft missing都在
pre-preparation階段停止，不偽造P3-C report。Successful submission保留Draft，P4-D不得刪除、rebase、
replace Draft或清editor state；Draft後續編輯／刪除是獨立明示player mutation，避免增加第三個
post-commit recovery location。

`SkillIdSource`第一個production consumer由P4-D2的`SkillDraftCreationService`擁有。Gramarye
composition root持有唯一`RandomUuidSkillIdSource`，且production `UUID.randomUUID()`只允許出現在該
adapter。Draft creation固定使用：

```java
Objects.requireNonNull(source.nextSkillId(), "skillIdSource returned null")
```

Service只接受authenticated `ServerPlayer`，由player UUID導出`SkillOwnerId`，要求P4-C Attachment Ready，
再以mint出的ID建立current empty Draft、呼叫P4-C `putDraft`完成immutable replacement，並將該caller-known
`SkillId`回傳。Mint不reserve Store、不證明owner、不保存credential、不跨restart，也不接受client UUID；
不建立Codec；collision最後仍由P3-D `ExpectedAbsent` commit裁決。

### Single Store authority and policy snapshot

P4-D不得把`ownerOf(skillId)`與`latestReference(skillId)`兩次read拼成authority。獨立Store-side port
提供同一server-thread observation：

```text
observeSubmissionAuthority(skillId, requester)
→ Absent(skillId)
→ Owned(latestReference)
→ ForeignOwned(skillId)
```

`Absent`表示owner與history/latest皆不存在；`Owned`只在history owner等於requester時返回Store max
latest；`ForeignOwned`不暴露actual owner或latest。Store owner／history／latest coherence破壞是
SubsystemUnavailable／programming invariant，不得偽裝成ForeignOwned。P3-C mapping固定為
`Absent → AuthorizedSkillState.New`、`Owned → Existing`、`ForeignOwned → Rejected(NOT_AUTHORIZED)`；
Attachment latest pointer不參與此snapshot。

唯一server-side policy owner為Gramarye composition root持有的`SkillSubmissionPolicyProvider`。
每個submission attempt恰呼叫一次`provider.snapshot(server)`，取得同一immutable
`SkillSubmissionPolicySnapshot`，其中`SkillQuota`交P3-D commit、`ValidationContext`交P3-C analyzer。
Facade、Store或analyzer不得自行建立第二份Unlimited／DEFAULTS，也不得在commit前重新取得quota。
V0唯一default provider是server-lifetime immutable，回傳`SkillQuota.Unlimited.INSTANCE`與
`new ValidationContext(MagicPolicyLimits.DEFAULTS)`，無reload；未來reload必須加入snapshot epoch並使
prepared handle失效。Provider回null或拋`RuntimeException`在Store mutation前形成bounded
SubsystemUnavailable；只保存exception class name，`Error`不捕捉。

### P3-C exactly-once and mutation boundary

Facade固定只走：

```text
authoritative Draft
→ SkillSubmissionInput.direct
→ DraftSubmissionPrechecker
→ SubmissionAuthorityChecker
→ SkillSubmissionPreparer
→ SkillSubmissionOutcomeMapper
```

每stage恰一次；不得重跑Reader／Writer／`resolveFromRaw`，不得額外呼叫resolver／analyzer／projector，
不得手工建立plan、validated definition或proposed revision，不得自行base check或自行merge report。只有
P3-C Prepared進persistence preflight。P3-C既有short-circuit及bounded report merge契約不變，
`SkillSubmissionPlan`仍是transient proposal，不是committed revision或credential。

Normal changed submission順序固定為：

```text
P3-C Prepared
→ prepare P4-C Attachment transition without publication
→ prebuild prospective Store carrier
→ prebuild prospective journal
→ prebuild prospective SavedData inner carrier
→ finish every byte/count/capacity/migration/chain check
→ fresh player/Attachment/Store/journal identity and authority recheck
→ SkillDefinitionStore.commit(plan, same quota) exactly once
→ publish Store carrier + journal
→ SavedData setDirty()
→ publish prepared Attachment transition
→ composition outcome
```

Store commit前必須排除所有一般document／Store／journal／carrier encode、migration、provider及capacity
failure；commit後不得首次執行這些工作或呼叫external callback。Typed Store failure丟棄全部prepared
values，Store、journal、Attachment及dirty不變，不自動retry／reprepare。

## 15. Composition outcome 與 report

P4-D建立獨立composition outcome，不得把`SkillSubmissionOutcome.Prepared`或P3-D Store result當作
final composition result。語意至少固定為：

```text
DraftUnavailable
SubsystemUnavailableBeforePreparation
PreparationRejected
PersistenceCapacityRejected
CommitConflict
QuotaRejected
CapacityRejected
IdentityRejected
SubsystemUnavailableAfterPreparation
Committed
CommittedPendingAttachmentRecovery
```

`PreparationRejected`只包裝既有P3-C non-Prepared outcome：Invalid、Conflict、IdentityRejected或
RevisionExhausted；constructor必須拒絕Prepared，且其report由被包裝outcome導出並保持exact same
reference。Draft missing、Attachment／journal／Store unavailable、policy provider unavailable等
pre-preparation outcome沒有P3-C report，也不得偽造空report。

一旦P3-C取得warning-only preparation report，PersistenceCapacityRejected、CommitConflict、
QuotaRejected、CapacityRejected、post-prepare IdentityRejected、SubsystemUnavailableAfterPreparation、
Committed及CommittedPendingAttachmentRecovery都保存exact same report reference；不得copy、merge、
normalize、rebuild或持久化，也不得放入journal、Attachment或Store。Tests必須`assertSame`。

`Committed`表示Store已commit、Store carrier／journal已publication並dirty，且Attachment in-memory
transition已publication；不表示playerdata durable、SavedData disk write成功、fsync或journal已clear。
`CommittedPendingAttachmentRecovery`表示Store已commit且journal已publication／dirty，但Attachment
publication未安全完成；不得rollback Store或clear journal。P3-D OwnerRejected對外只映射
`IdentityRejected(NOT_AUTHORIZED)`，不得洩漏actual owner或latest。

P4-C same-pointer transition在Attachment domain是合法no-op，但正常P4-D submission若proposed target
等於current Attachment pointer，屬stale／programming invariant：不commit、不append journal、不dirty，
回bounded SubsystemUnavailableAfterPreparation或固定invariant rejection。不得將它視為successful
duplicate commit；只有recovery入口可將loaded target視為already-applied。

## 16. Store-first recovery journal

### Zero sentinel and physical framing

P4-D對`pending_attachment_updates_blob`的解釋與§5一致。Payload length恰為0時是唯一canonical empty
journal：不呼叫NBT parser、不執行migration、不建立non-zero root，count與encoded bytes均為0，
`rewriteRequired=false`。Non-zero V0中`entries`為empty list是合法但非canonical empty journal；load成功
且`journalRewriteRequired=true`，下一次安全publication改寫為zero sentinel，不形成第二種canonical
empty representation，也不只因非canonical而停用Store。

Non-zero payload唯一framing為：

```text
NbtIo.writeAnyTag(rootCompound, DataOutput)
= one CompoundTag type byte + complete CompoundTag payload
```

它沒有root name或zero-length UTF root-name framing。Decoder要求exactly one Tag、root type恰為
CompoundTag且byte-array EOF立即成立；任意trailing byte拒絕。`NbtIo.writeUnnamedTag`禁止，
`writeAnyTag != writeUnnamedTag`，不同路徑不得混用或以`+2`補償。

### Journal V0 exact physical schema

Current V0 non-zero root exact fields為：

```text
CompoundTag {
  journal_schema_version: IntTag(0),
  entries: ListTag<CompoundTag> [
    CompoundTag {
      owner: IntArrayTag[4],
      skill_id: IntArrayTag[4],
      expected_attachment_generation: IntTag,
      target_attachment_generation: IntTag,
      expected_pointer?: CompoundTag {
        skill_id: StringTag,
        revision: IntTag
      },
      target_pointer: CompoundTag {
        skill_id: StringTag,
        revision: IntTag
      }
    }
  ]
}
```

Root與entry Compound不得有unknown、missing required、wrong-type或duplicate fields；`?`只由field
absence表示，不新增`has_expected_pointer`。Owner與route SkillId分別重用`SkillOwnerId.CODEC`／
`SkillId.CODEC`在NbtOps下的`IntArrayTag[4]`；pointer重用`SkillReference.CODEC`的exact
String-UUID／Int-revision Compound shape。Journal不得保存document、Draft、report、plan、quota、player
name、任意diagnostics或checksum truth。

### Strict decoder and migration

P4-D1必須使用single schema-aware streaming decoder，在general Compound materialization前完成root
type、duplicate fields、schema probe、該supported version的exact fields/types、entries element type、raw
count、nested UUID/reference shape及trailing EOF驗證；current V0使用本節exact whitelist，未來legacy
version則必須有自己受核准的strict physical grammar，不能先套current-only whitelist而使migration不可達。
不得以`CompoundTag` last-write-wins結果冒充strict decode、先Map化entries、回partial DTO或使用
`NbtAccounter.unlimitedHeap()`。若實作另用`NbtAccounter`，必須finite並以golden test證明合法maximum
不被誤拒；不得新增journal-specific MagicSafetyCeilings constant。Decoder不得原地修改input bytes；
physical DTO與每個migration input皆immutable，每一步只建立fresh output，不得原地修補欄位或entry。

`journal_schema_version`是唯一journal migration axis。唯一production provider為
`PendingAttachmentJournalMigrationPlans.production()`；plan immutable、from-version unique、adjacent、
sorted、exact coverage，current V0 production plan為empty，caller不能注入production plan。Non-zero流程：

```text
strict physical root framing
→ schema probe
→ adjacent journal migration
→ strict current V0 decode
→ canonical immutable journal
```

Zero sentinel不進migration。Missing edge、future schema、partial或migration `RuntimeException`形成journal
Unavailable並保留原opaque bytes；只保存bounded exception class name，`Error`不捕捉。

### Byte/count coordinates and failure precedence

`MAX_PENDING_ATTACHMENT_JOURNAL_ENCODED_BYTES = 1_048_576`量測ByteArray raw payload；non-zero時恰等於
上述`writeAnyTag` bytes。0是sentinel；1..1_048_576可進strict framing；1_048_577在parse前形成
EncodedCapacityExceeded。ByteArray length prefix、field framing、SavedData inner／whole-root與gzip均不計。
Exact maximum只是outer guard合法，不保證V0 canonical journal可生成該尺寸。

`MAX_PENDING_ATTACHMENT_UPDATES = 4_096`計算raw entries List count。Duplicates與noncanonical order都
計入，且在dedup／semantic validation前計入；exact 4096合法，4097在entry DTO配置前拒絕。不得另建
per-owner／per-skill count ceiling。

相同ordered bytes的first-failure precedence固定為：

```text
encoded byte over-cap
→ malformed root framing/trailing
→ duplicate physical field
→ missing/unknown/wrong tag type
→ unsupported/future schema or missing migration edge
→ journal migration failure
→ raw entry count over-cap
→ first input-order malformed entry
→ generation invalid/overflow
→ pointer/route mismatch
→ duplicate stable key
→ broken continuous chain
→ Store target audit failure
→ canonical rewrite comparison
```

Capacity不得稱為Malformed，migration failure不得稱為chain failure，Store target missing不得稱為decode
failure。Failure只保存machine code、bounded scalar／route／index與bounded exception class name。

### Entry invariants, canonical ordering and chains

每筆generation固定為Java `int`／NBT `IntTag`且非負；expected必須小於`Integer.MAX_VALUE`，target必須
等於expected + 1。P4-D不得自行計算successor，target generation只能來自P4-C唯一checked helper。
Expected pointer存在時與target pointer都必須route至entry SkillId；target必須存在且不得等於expected。
Owner、SkillId及所有present pointer皆不得為null。Journal只保存P3-D已commit target reference，不配置
`SkillRevision`。

Stable key固定為`(owner, skillId, targetAttachmentGeneration)`；duplicate是typed corruption，不採
first-wins、last-wins或dedup。Canonical order固定為owner UUID natural order、SkillId UUID natural
order、target generation ascending。Decode保留原input order直到shape、semantic與duplicate檢查完成；
合法但noncanonical order load成功、canonicalize並設`journalRewriteRequired=true`。

同owner＋skill允許多筆pending，但依target generation排序後必須形成單一bounded continuous chain：

```text
entry[n + 1].expectedGeneration == entry[n].targetGeneration
entry[n + 1].expectedPointer == Optional.of(entry[n].targetPointer)
```

第一筆expected pointer可empty且expected generation可為任意非負int。Generation gap、pointer gap、branch、
同target generation或multiset-only validation都形成整個journal Unavailable；不得刪除壞entry、保留
partial chain或藉重排掩蓋corruption。

### Operational state, Store audit and roots

P4-D derived operational state固定為：

```text
PendingAttachmentJournalState
├─ Ready(canonical immutable journal, matching canonical bytes/zero sentinel, rewriteRequired)
└─ Unavailable(bounded journal failure)
```

它不是第二持久化truth；P4-B SavedData的exact opaque pending blob是唯一persistent pending-transition
truth。Physical/domain decode本身不查Store；bootstrap decode成功後由單一Store-side audit檢查每個target
reference存在、owner等於entry owner且route等於entry SkillId。任一失敗形成
JournalTargetAuditUnavailable，不猜Store latest、不移除entry、不提升Attachment或clear journal。

Journal Unavailable時：Store find/latest/owner/count及pin/close保持可用；submission prepare/commit、
journal append/clear、recovery與production reclaim composition停用；journal root projection回Unavailable，
P4-E global root completeness為false。不得把blob當empty、把合法Store稱為Quarantined、停用所有Store
read、自動repair／delete，或overwrite原bytes；不得僅因journal failure將P4-B Store SavedData轉成
Unavailable，也不得建立automatic backup／sidecar。Original opaque pending bytes保持exact immutable，
P4-D不dirty、不替換；若P4-B因獨立既有合法原因save，仍逐byte寫回同一blob。V0沒有in-place repair
API，operator修復後以restart重新bootstrap。

Ready journal提供`PendingAttachmentJournalRootProjection.Available`，每筆target pointer恰為一個root，
依canonical journal order輸出，cross-entry duplicate可保留，最大數由4096承保而不新增root ceiling。
Unavailable不得回empty roots。P4-D不建立Complete root snapshot、不合併player/runtime roots、不枚舉
offline players、不呼叫reclaim；P4-E看到Unavailable必須維持Incomplete。

### Canonical rewrite, Store port and publication

Migration、noncanonical order、non-zero empty journal或valid current bytes不等於canonical writer bytes時可
要求rewrite。只有完整decode、chain valid及Store target audit通過後，才能prebuild canonical pending
bytes與new SavedData inner carrier、替換matching journal Ready/cache identity、publish new SavedData Ready，
最後`setDirty()`。不得在partial decode或Unavailable時rewrite／dirty，不得由truncated facts推導rewrite，
也不得只替換cache而不替換SavedData carrier。

P4-D1建立獨立public窄port：

```text
com.yo1no.gramarye.magic.definition.store.SkillDefinitionStoreSubmissionPort
```

Port由P4-B lifecycle/composition建立並注入P4-D；一般read/pin/reclaim service不擴張。它只提供single
authority snapshot、prepare／commit opaque Store-journal handle、journal readiness/root status，以及
recovery journal replay／clear所需窄操作；不得公開raw Store、`EncodedSkillStoreCarrier`、SavedData Ready、
pending bytes、bare-document direct commit或arbitrary journal replacement。

Prepare handle綁定exact server、SavedData Ready／base carrier／journal identities、same immutable policy
snapshot、prospective Store carrier、journal與inner carrier；prepare不commit、不dirty、不碰Attachment。
Commit重新驗證全部identity及fresh authority，呼叫`SkillDefinitionStore.commit`恰一次。Typed failure零
publication；Committed後publication先於dirty。若commit後發生runtime pairing invariant，沿P4-B既有
Unavailable fail-closed政策處理，不rollback Store、不保存stale carrier、不捕捉`Error`／OOME。

### Recovery chain and durable clear

對同owner＋skill的canonical chain `e0..eN`，later persisted playerdata load的Attachment state：

- 等於chain base expected：依序replay全部entries至final target，journal全部保留；任一replay失敗即停，
  不clear、不自動retry branch，並回bounded typed recovery failure。
- 等於中間`eK.target`：這是prefix persisted readback證據，清除`e0..eK`；若仍有suffix，再依序replay至
  final target，suffix保留。
- 等於final target：清除整條chain，不呼叫`setData`。
- 既非base expected也非任一target：RecoveryConflict，journal保留，不setData、不clear。
- Store target missing或owner mismatch：RecoveryTargetInvalid，journal保留且不提升pointer。

`setData`成功絕不是durability ack。Safe clear只來自later playerdata load對persisted pointer／generation的
matching證據。Clear先prebuild remaining journal bytes與inner carrier，驗證exact current Ready／journal
identity，再publish、`setDirty()`並隨即return；不改Store或Attachment。若clear尚未落盤便crash，old
journal可重現，loaded target再次確認及clear必須idempotent。

P4-D0不固定具體event class，但固定ordering contract：P4-B Store install完成 → P4-D journal bootstrap與
其要求的safe canonical rewrite publication完成 → 才接受submission、recovery、journal root projection
或P4-E reclaim composition。P4-D3開始前必須以鎖定source選定唯一event，證明integrated／dedicated／
GameTest中所有正常player login前bootstrap／rewrite完成，且save callback不與journal publication並行；
若找不到安全event即停止D3，不以lazy race-prone decode取代。

Store-first只承諾server-thread in-memory mutation order與scheduled persistence，不是跨檔transaction。
鎖定1.21.1 path的playerdata replacement是同步操作，而world SavedData使用分離的deep-copy／queued
write；平台不提供兩者的atomic durable commit，故process crash可能留下已持久化target Attachment搭配
舊Store／journal。P4-D不得宣稱journal能復原不存在於persisted Store的target，也不得宣稱fsync或
durable write ordering；後續P4-E只能依Store truth對missing reference做fail-closed reconciliation。
Crash/restart tests必須將此平台外層window列為known limitation，不能以sleep或未鎖定flush timing冒充
原子性證明。

### Dirty matrix and combined fixed-heap obligation

Journal read／root projection、Unavailable、valid canonical bootstrap、preparation rejection、preflight
failure、typed Store failure、recovery-only `setData`及journal-clear no-op都不改Store SavedData dirty。
Valid migration／canonical rewrite、Store commit＋journal publication及persisted-target-confirmed prefix
clear在publication後dirty。Attachment publication success不額外dirty；publication failure保留已dirty
journal。Journal failure不得清除既有dirty或把pending改成zero。

P4-D完成前必須有單一process的fixed
`-Xms512m -Xmx1024m -XX:+ExitOnOutOfMemoryError` combined Gate，同時保留至少63 MiB current Store
carrier、full prospective carrier、4096-entry cap下largest valid canonical V0 journal、prospective inner
carrier、platform SavedData deep copy、P3-C plan／validated definition／warning report、prepared Attachment
transition、current Attachment Ready及journal root projection，並實際完成prepare → preflight → commit →
Store/journal publication → dirty → Attachment publication → save → restart → recovery／clear。Exact
1_048_576／+1及4096／4097另由byte/count tests覆蓋；heap workload不得用invalid padding湊1 MiB。

Gate在1 GiB OOME／timeout時P4-D停止且P4-E不得開始；不得降低Store或entry count、移除deep copy、拆成
各自Gate或提高heap後宣稱原契約通過。唯一出口是先做P4-0 minimum-heap-floor authority修訂、獨立
commit／remote CI，再以新floor重跑相同combined Gate。

## 17. Reconciliation

- Store owner／documents 是 truth。
- Attachment pointer 存在、Store reference 存在且 owner 匹配：保留，即使不是 Store latest。
- Offline audit 發現 pointer 不存在於 Store 或 owner mismatch 時，只回
  `ReconciliationRequired(Deferred)`：disk 不變、global audit `Incomplete`、reclaim invocation 0。
  P4-E V0 明示接受永久 offline stale player 可長期阻擋 reclaim。
- Online prune 只屬 P4-E2，且必須在該次 login 的 P4-D recovery 完成後：觀察一份當下
  Ready Attachment，對全部 latest／equipped claims 作 grouped Store audit，建立完整 immutable
  replacement，並最多呼叫一次 `setData`。
- Stale／foreign latest 只能使用 P4-C 唯一 generation arithmetic 修剪並增加 generation；
  stale／foreign equipped 可修剪但不改 generation。Valid nonlatest exact reference 必須保留，
  不 promotion 到 Store latest，owner mismatch 不洩漏 actual owner。
- 任一 latest generation 已為 `Integer.MAX_VALUE`、player／state identity drift 或 Ready carrier
  rebuild failure 使整批零 publication：不修改 Store、journal、Draft 或 editor。
- Journal target 有效：replay 或確認。
- Journal target 不存在或 owner 不符：typed reconciliation failure，不提升 pointer。
- 無 journal 的舊 pointer：不自動提升到 Store latest。
- Duplicate persisted route／slot在P4-C load形成Quarantined；不得repair、first-wins或
  last-write-wins。Platform materialization前已消解的Compound同名field不在custom serializer
  可觀察邊界。
- 玩家移除 pointer：保留移除；Store 與 quota 不變。
- Orphan revision：不自動刪除、不釋放 quota。
- Audit N 發現需對帳後，當輪及後續 login prune／save 都不 reclaim；只有下一次
  server restart 的 Audit N+1 完整重讀所有 source，才可能產生 fresh `Complete`。

### P4-E0-B.5：production trigger 與 shared audit-service ownership

本subsection是production `SkillRetentionRootAuditService`建構、長期owner、login trigger、
exact identity injection與E2／E3 reuse的唯normative authority；不保留A／B／C多方案。
唯一裁決為：

| Authority coordinate | Unique decision |
| --- | --- |
| 首次加入production construction的engineering phase | P4-E2 |
| runtime長期lifecycle owner | 既有`SkillDefinitionStoreService` |
| 每個Store-service composition instance的audit service數量 | exact one `final SkillRetentionRootAuditService` |
| player-login event owner | sole `SkillSubmissionRecoveryService` |
| P4-E2與P4-E3使用的audit-service identity | exact same object identity |
| P4-E3 production constructor-call delta | 0 |
| P4-E2 closure是否需production login wiring | 需要，且必須active |

#### Construction 與 lifecycle ownership

Production construction唯一固定為：

```text
Gramarye composition
→ construct exact SkillDefinitionStoreService
  → that Store service constructs and owns exact one final
    SkillRetentionRootAuditService
```

每個exact `SkillDefinitionStoreService` object在composition建立時建構並長期持有一個
exact `final SkillRetentionRootAuditService`；該service於任何login reconciliation前已存在。
在同exact Store-service composition instance內，server start／stop／restart不替換Store-service owner
或audit-service object。Per-server slot仍以exact `MinecraftServer` object identity隔離；
server stop只移除對應slot，不銷毀、替換或lazy-recreate service owner。新exact server
object由same audit-service instance建立新的identity-isolated slot。

禁止static singleton、global registry、service locator、lazy-per-login construction、
`SkillSubmissionRecoveryService` direct construction、P4-E3 construction或replacement。Production
`SkillRetentionRootAuditService` constructor callsites必須恰為1；該唯一callsite屬於
`SkillDefinitionStoreService`或其exact package-private construction helper，並必須使任意caller
無法提供、替換或配對audit-service identity。未來production static Gate必須同時
證明callsite count、所屬owner／helper與arbitrary-caller exclusion。P4-E3 constructor calls固定為0。

#### Sole login owner 與 synchronous ordering

`SkillSubmissionRecoveryService`繼續是sole `PlayerLoggedInEvent` owner。既有handler只能窄幅
延伸為：

```text
PlayerLoggedInEvent
→ validate exact current ServerPlayer
→ invoke and complete P4-D recovery
→ retain the typed recovery outcome
→ pass that outcome to the P4-E2 reconciliation dependency
→ complete the P4-E2 continuation
→ return
```

整條鏈必須在same server logic thread、same synchronous call chain內完成；no yield、
no future／executor、no second event dispatch、no cross-tick plan，也不可callback至未審查的
external code。不得新增第二個P4-E2／P4-E3 login listener，不得依event registration
order協調兩個handler，也不得建立next-tick、background、periodic retry或
admin／manual reconciliation入口。P4-E2在P4-D recovery完成前不得觀察或修改
Attachment。

B.5只固定：P4-D recovery invocation完成後，typed outcome必須被保留並傳給
E2-facing dependency。B.5不裁決哪些recovery outcomes允許reconciliation、哪些必須
`NoChanges`、`Failed`或`Deferred`、Unavailable是否執行E2，也不裁決recovery
mutation後的fresh-observation規則。這份outcome matrix只能由B.5 closure後、從clean
HEAD重開的P4-E2 read-only design review裁決；B.5不推導任何outcome的後續語意。

#### Exact-identity constructor/composition injection

`SkillSubmissionRecoveryService`不得建構audit service、接收任意caller-provided audit
service、使用static accessor／service locator／per-call supplier、以generic callback作為
authority，或透過reflection取得Store internals。它在production composition時只接收
一個窄的、constructor-injected E2 reconciliation dependency／coordinator。

該dependency在composition-time已同時綁定：

```text
exact SkillDefinitionStoreService object identity
+ that Store service's exact final SkillRetentionRootAuditService object identity
+ P4-E2所需的其他exact dependencies
```

### Counting coordinates and first-failure order

- `directory_entries`：每個實際 directory entry 在任何分類前計 1；ignored、temp、hidden、
  corrupted-backup 與 unknown irrelevant entries 仍消耗額度。Baseline／final entry-set race
  fail closed。
- `relevant_records`：每個被選為authoritative player source的unique owner UUID計1；source kind
  可以是`ONLINE_PLAYER_ATTACHMENT`、`INTEGRATED_RUNTIME_SNAPSHOT`、`DISK_PRIMARY`或
  `DISK_OLD`。同UUID primary／old pair最多形成1筆；online或integrated勝出時，同UUID disk pair
  形成0筆。Missing online Attachment仍是zero-root relevant record；Quarantined online Attachment
  先消耗1筆，再於online state checkpoint形成`Incomplete`，不退還counter。Maximum `2_048`
  inclusive；第`2_049`個selected authoritative owner立即
  `COUNTER_CAPACITY_EXCEEDED(relevant_records, 2_049, 2_048)`。
- `compressed_bytes_per_file`：對selected disk source，從 gzip 第一個 header byte 到 physical EOF，包含 optional
  header、deflate、trailer 與 trailing physical bytes。先驗 per-file，再 checked-add
  `compressed_bytes_total`；只累計實際選中並進入 strict ingress 的 player sources。
- `decompressed_bytes_per_file`：對selected disk source，為unnamed Compound root 的 type byte／zero-length UTF root
  name／complete payload／root EndTag／exact decompressed EOF；先驗 per-file，再
  checked-add `decompressed_bytes_total`。
- Root Compound depth 為1。Compound／List 每次 container entry、scalar-tag kinds 精確沿用
  locked research-scanner classification，不自行擴張或縮減。Compound field 在 field-name
  materialization 前計數；List 在配置／處理 elements 前以宣告 length 計數；
  ByteArray／IntArray／LongArray 在配置或讀 payload 前以宣告 element length 計數。
- `modified_utf8_bytes_*` 計 Compound field name 與 StringTag payload 的 modified-UTF
  payload bytes，不含2-byte length prefix。同一 event checkpoint 永遠 per-file 先於
  aggregate。
- `attachment_admissions`：selected disk／integrated source有non-null
  `gramarye:player_skills` Tag且完整呼叫一次P4-C admission core才計1。Missing key計0；
  Ready計1；PreservedRaw／OversizeMarker計1但使global result `Incomplete`；key存在卻沒有
  完整admit不得算成功。Online source只觀察已由正常登入流程admit的現存state，本次audit
  固定+0，不得重跑admission。

### Overrun and heap policy

任一 counter overrun 都使 global root audit `Incomplete`、reclaim calls 0、source mutation 0，
但server startup繼續。`INCOMPLETE_AND_CONTINUE`表示停止本次authoritative capture、釋放
audit-local state後繼續startup，不是繼續無界掃描。不得把超限player當zero roots、
刪掉claims後重試、修改playerdata、abort startup、自動提高ceiling，或永久將
P4-B Store轉成Unavailable。

Audit 進入前唯一 normative heap-floor observation coordinate 固定為：

```java
HotSpotDiagnosticMXBean diagnostic =
        ManagementFactory.getPlatformMXBean(
                HotSpotDiagnosticMXBean.class);

VMOption option =
        diagnostic.getVMOption("MaxHeapSize");

long effectiveMaxHeapBytes =
        Long.parseLong(option.getValue());
```

`VMOption.value` 必須符合 canonical base-10 nonnegative `long` grammar
`0|[1-9][0-9]*`。Effective `MaxHeapSize < 1_610_612_736` 固定為
`HEAP_FLOOR_NOT_MET`；大於或等於 floor 固定為 `QUALIFIED_FLOOR_PRESENT`。Bean 或 option
不存在、value 非 canonical／為負／overflow，或核准 observation API 拋
`RuntimeException`，固定為 `HEAP_FLOOR_UNVERIFIABLE`；不得捕捉 `Error` 或
`OutOfMemoryError`，也不得把 unverifiable 當 qualified。

`HEAP_FLOOR_NOT_MET` 與 `HEAP_FLOOR_UNVERIFIABLE` 都回 global `Incomplete` 且 startup
繼續；directory work、file open、journal observation／projection、Attachment admission、raw-root
capture、Store target audit、reclaim calls 與 source mutation 都必須為 0。
`QUALIFIED_FLOOR_PRESENT` 只表示有資格嘗試，不保證其他 counter 仍在界內或沒有 runtime
failure。

`Runtime.maxMemory()` 是 collector-specific diagnostic only；
`MemoryMXBean.getHeapMemoryUsage().getMax()`、各 collector
`MemoryPoolMXBean` max 與 pool peak sum 全部只可作 diagnostic／test report。它們不得決定
pass／fail、覆蓋或 fallback effective `MaxHeapSize`、彼此取 min／max，或套用 tolerance、
epsilon、百分比／collector-specific allowance、alignment allowance、rounding compensation。
Requested `-Xmx` token 與 heap-pool總和也不得作 authority coordinate。

正式 process-control 角色固定如下；它們是測試 controls，不是新的產品 ceiling：

- `-Xms512m -Xmx1536m -XX:+ExitOnOutOfMemoryError` 在 locked runtime 可用的 G1、Parallel、
  Serial、ZGC 均須觀察 effective `MaxHeapSize = 1_610_612_736` 並分類
  `QUALIFIED_FLOOR_PRESENT`；即使 `Runtime.maxMemory()` 較低也不得誤判。
- Locked Temurin JDK 21.0.8+9／macOS aarch64 的 `-Xmx1535m -XX:+UseG1GC` 觀察
  effective `1_610_612_736`，是 `ALIGNED_TO_FLOOR_CONTROL` qualified positive control，
  不是 negative／below-floor／rejection control。
- `-Xms512m -Xmx1024m -XX:+UseG1GC -XX:+ExitOnOutOfMemoryError` 觀察 effective
  `1_073_741_824`，是 `HEAP_FLOOR_NOT_MET` process control 且 source work 0；1,024 MiB
  不是另一個 P4-E product heap tier。
- CLI heap alignment不能可靠形成 exact floor − 1；pure injected observation seam 必須證明
  floor − 1 → `HEAP_FLOOR_NOT_MET`、floor／floor + 1 → `QUALIFIED_FLOOR_PRESENT`。不得再搜尋
  1,534 MiB 或其他近 floor CLI token。

Floor 數值只能稱為 **P4-E V0 product-selected audit heap floor and fixed-heap qualification
tier**，不得稱為 universal safe minimum、empirically proven lowest heap、Minecraft／NeoForge
requirement 或所有 platform 的安全保證。

R2Q sampled evidence的exact-positive case 00 peak為`1_499_741_840`bytes，headroom
`110_870_896`bytes／`6.883771221%`。最窄sampled headroom是case 11

### Directory, playerdata truth, and strict ingress

Canonical active playerdata names只有lowercase canonical UUID的
`<uuid>.dat`與`<uuid>.dat_old`，ASCII／UTF-8長度分別為40與44bytes，不新增filename
length ceiling。Uppercase UUID、parseable但noncanonical UUID、case alias 或UUID-shaped malformed
active name使global `Incomplete`。Platform temp、hidden、`_corrupted_` backup 或明顯無關名稱
可ignore，但仍消耗directory counter。

Directory使用`NOFOLLOW_LINKS`，必須是non-symlink directory且`fileKey != null`，並比較
baseline／final identity與entry set。Relevant path必須是non-symlink regular file、
`fileKey != null`，在pre/open/post/final保持size／mtime／fileKey／classification且從同一
channel讀取。Symlink、directory、special file、null fileKey或race一律`Incomplete`。不使用
`Files.readAllBytes`、`Files.notExists` 作唯一absence truth、stock
`PlayerDataStorage.load`、background sweep或path retry loop。

Playerdata primary／old truth-selection matrix為：

| Disk state | P4-E selected truth |
| --- | --- |
| strict-valid current primary + arbitrary old | primary；old不讀 |
| stable primary absent + strict-valid current old | old |
| stable primary／old皆absent | 無record／zero roots |
| primary有可證明platform-read failure + strict-valid current old | old；audit不建立backup |
| primary platform-read failure + old missing／unreadable | `Incomplete` |
| primary只有P4-E strict-grammar rejection + any old | `Incomplete`；不fallback old |

`platform-read failure`與P4-E額外strict grammar rejection必須分開。Strict-only包括second gzip

member、trailing、zero padding、bad magic／method／flags、invalid FHCRC／trailer、
truncation與compressed／decompressed MAX+1；不複製第二套gzip truth framework。

payload、root EndTag、exact decompressed EOF、finite accounting與depth 512；第513層拒絕。

array／list／string length。

Snapshot沒有stream EOF；logical encoding在root EndTag後立即結束。此座標不是原始

`CompoundTag.copy()`作量測前置，也不得加second whole-tree checksum traversal。

snapshot內的disk-version field。P4-E不要求、不讀取、不驗證snapshot內的

runtime snapshot。Minecraft level-load的100MiB accounter不是P4-E authority，不建立
`MAX_LEVEL_DAT_*`。

source-set freshness witnesses；online initial／final witness依前節獨立保存與驗證，不以integrated
witness替代。在structural count、full P4-C admission與root projection完成後，

thread、profile仍存在且UUID相同、snapshot仍是exact same object reference，且其他

`Incomplete(INTEGRATED_OWNER_FRESHNESS_LOST)`、discard partial roots、reclaim 0；不retry、不merge
第二次觀察、不當zero roots，不跨tick保存snapshot或把它當index truth。

Reference identity無法偵測第三方對同一`CompoundTag` object的敵對in-place mutation。V0
保證只包含server logic-thread confinement、同一synchronous call chain、Gramarye traversal／

Off-thread、reflection、Unsafe或違反platform thread contract的敵對mutation不在V0完整性保證內。

background watcher。未來E1 Gate必須證明traversal與root projection不修改input Tag。Full

Integrated branch只在上述global checkpoint 13執行source-local work；checkpoint 8～12已先完成
online identity、integrated four-state、全域arbitration、selected-owner UUID sort及該owner的
relevant-record checkpoint。Disk source的現有stream子順序不變。Integrated source跳過per-file
compressed、aggregate compressed addition與gzip，然後依序執行
logical per-source decompressed width → aggregate decompressed checked-add → structural counters →

### Completeness, index, lifecycle, and reclaim

每個enabled family輸出`Complete(family summary)`或`Incomplete(machine reason)`。Global
`Complete`只在以下同時成立時可建立：closed inventory及provider coverage完整；directory、
entry set與每UUID恰一selected source穩定；所有selected owners已按統一UUID natural order處理；
25 counters全部未超限；所有accepted disk records都是`IntTag(3955)`，所有selected integrated
sources都滿足post-DFU logical-coordinate與final identity freshness規則，所有selected online
sources都是Missing或Ready且通過final identity／presence／state freshness recheck，且P4-E DFU calls
精確為0；P4-C Attachment都是Ready或missing；journal roots Available；
沒有pending reconciliation；raw roots不超65,536；Store exact-reference／owner audit成功；
heap observation 為 `QUALIFIED_FLOOR_PRESENT`；freshness window仍有效。任一條件失敗都不得建立
`Complete` snapshot。

World-level root index固定memory-only、每次startup重建，restart初始`Incomplete`。它只可
保存bounded source family、stable source ID／kind／ordinal、SkillReference與per-source
status，以及下文固定的generation／state／lease bookkeeping與同一audited single backing；
禁止raw playerdata／Attachment、SkillDocument、Store owner／latest truth、carrier、
`SkillRetentionRootSnapshot.Complete`或可跨tick的public Complete permit。Source永遠勝過index；
任一source變化、race或reconciliation立即使index `Incomplete`，server stop移除exact
server-identity index。

#### Memory-only index generation authority

Index generation的唯一owner固定為：

```text
one exact SkillRetentionRootAuditService object identity
× one exact MinecraftServer object identity
```

`SkillRetentionRootAuditService`的production construction、long-term owner與E2／E3 exact-identity
reuse唯一依據§17的P4-E0-B.5。該construction authority不改變本節service×server
generation owner、`long` coordinate、reservation、publication、exhaustion或lease語意。

每個audit service擁有自己的index lifecycle，service內每個exact server object identity有獨立
generation slot。不採global static、cross-server shared、per-Complete owner、server tick、P4-C
Attachment mutation generation、Store revision、journal generation或SavedData identity。`MinecraftServer#getTickCount()`
仍只是same-call-chain coordinate，不是index generation。Index generation不持久化、不序列化、
不寫入SavedData，也不進R2Q profile。

Generation的Java／domain type唯一固定為`long`，合法值是`0..Long.MAX_VALUE`。Negative、
wrap與saturation後繼續運作全部禁止。No exact server slot表示index authority是`Incomplete`且沒有
published generation；新slot的internal baseline generation固定為0，0不表示已有成功
audit。First accepted audit reservation使用1。

#### Reservation, consumption, and publication

只有兩種operation消耗index generation：

1. accepted global audit attempt reservation；
2. P4-E2 explicit index invalidation。

One accepted operation只能reserve一次。Audit的success、`Incomplete`、`OverLimit`、
`ReconciliationRequired`、final freshness failure、operational `RuntimeException`、`Error`／OOME
都不得再增加generation。Complete permit成功consume或misuse、handoff open／close、
server stop／`removeServer`、result construction與diagnostic read也不消耗generation。

Global audit入口順序固定為：

```text
null／programming checks
→ exact server object identity
→ same server logic thread
→ reentrant／active-lease invariant checks
→ reserve next index generation
→ invalidate old Complete／index authority
→ effective MaxHeapSize Gate
→ 既有18-step P4-E root／source order的剩餘checkpoints
```

Null／programming／wrong-server／wrong-thread／reentrant／active-lease failure發生在reservation前，
generation delta與index delta都為0。Reservation成功後，若current generation為`g`，reserved為
`g + 1`；舊Complete authority及backing立即失效，index先進入該reserved generation的
`AuditInProgress`非Complete state。Heap floor、Store、journal、B1、B2-A reconciliation、
final freshness或其他後續failure都不得恢復舊Complete。

所有normal terminal都在同一reserved generation發布：

```text
audit success                  -> CompleteIndex(reserved)
audit Incomplete               -> IncompleteIndex(reserved)
audit OverLimit                -> IncompleteIndex(reserved)
audit ReconciliationRequired   -> IncompleteIndex(reserved)
final freshness failure        -> IncompleteIndex(reserved)
operational RuntimeException   -> IncompleteIndex(reserved)
Error／OOME                     -> original Error／OOME propagates
                                  and index remains non-Complete at reserved
```

Success、failure、freshness與result publication均不再advance generation。Success publication必須是單一
state replacement，不得逐項發布partial index。`Error`／OOME不捕捉、不轉成bounded
runtime failure，但舊Complete不得因此復活。

#### Exhaustion and E2 invalidation

`Long.MAX_VALUE - 1 -> Long.MAX_VALUE`是最後一次合法reservation。Current generation已是
`Long.MAX_VALUE`時，audit或E2 invalidation不得加1、wrap、saturate、reset或保留舊
Complete。該operation在source work前清除舊Complete permit authority與audited backing，以新的
exact state identity進入：

```text
GenerationExhausted(generation = Long.MAX_VALUE)
-> Incomplete(GENERATION_EXHAUSTED)
```

此路徑的source work、root capture、Store audit、snapshot與reclaim均為0，startup繼續且source
data不變。`GENERATION_EXHAUSTED`只綁定本index generation coordinate，不可解釋成
P4-C、Store或journal generation。Exhausted對該exact server slot是terminal；repeated audit或
E2 invalidation均回同一bounded `Incomplete`，generation保持MAX，不重試或重建baseline。
只有exact server stop後的`removeServer`可刪除該slot。

P4-E2未來只可經package-private reviewed seam使index失效。沒有active handoff且current
`g < Long.MAX_VALUE`時，one accepted invalidation只reserve `g + 1`一次，丟棄Complete backing／
permit authority並發布`IncompleteIndex(g + 1)`。Current已是MAX時進入上述
`GenerationExhausted`。E2 invalidation不得重audit、project roots、保留舊Complete、建snapshot、
reclaim或修改Store／journal。同一次E2 reconciliation batch只觸發一次invalidation，
不按stale pointer數增加generation。

#### Complete permit and active handoff lease

未來Complete permit的所有consume attempt先以不可逆方式標記permit used；second use固定
fail fast。Wrong service／server／thread／tick／state identity／generation同樣先consume，並清除
permit自身持有的authority references後回programming／lifecycle failure。Misuse不增加index
generation、不修改目前index、不覆寫其他合法`CompleteIndex`，且不可retry。
Generation mismatch代表舊permit已自然失效，不授權它破壞較新index。

成功consume後的internal transition固定為：

```text
CompleteIndex(g)
-> CompleteIndexWithActiveLease(g)
```

Generation與audited backing identity不變，只新增exact lease identity；permit已consume。Handoff綁定
service、server、thread、tick、active-lease state identity、generation、lease identity與single iterator
state。Handoff close將同一backing從`CompleteIndexWithActiveLease(g)`放回`CompleteIndex(g)`，
generation不變、不建second root vector、不重新發行Complete permit；原public Complete仍是used。

Active lease期間，new audit與E2 invalidation皆為programming／lifecycle fail-fast，generation delta為0且
index／lease不變。第二個Complete consume attempt先consume該permit再fail fast，不改active
lease。Server stop／`removeServer`是唯一強制清理例外：它使handoff失效、清除cursor／
lease authority及backing、移除exact server slot且不增加generation；後續handoff操作固定拒絕。
不使用Cleaner、finalizer或background lease timeout。

#### Removal, restart, and state identity

`removeServer`只由未來P4-E3在既有`SkillDefinitionStoreService` sole
`ServerStoppedEvent` lifecycle chain中，對§17 B.5的exact same audit-service field呼叫。Normal remove清除
`Incomplete`／`Complete`／`GenerationExhausted`與active-lease state，並清除backing、permit、
lease references，最後刪除exact server object identity slot；generation不增加且不持久化。
不得對live server先remove再reinsert以繞過exhaustion或重建baseline。
不同的new `MinecraftServer` object identity建立新slot並從internal baseline 0開始。同一已
stopped server object不得重新進入normal audit lifecycle；這是programming／lifecycle misuse，
不是generation reset。Restart仍是memory-only index不存在 → `Incomplete` → full startup audit。

Internal state machine至少包含：

```text
NoEntry
Incomplete(g)
AuditInProgress(g)
CompleteIndex(g)
CompleteIndexWithActiveLease(g)
GenerationExhausted(Long.MAX_VALUE)
Removed
```

固定轉移為：

```text
NoEntry -> baseline 0 -> audit reservation 1 -> AuditInProgress(1)
Incomplete(g) -> audit reservation g+1 -> AuditInProgress(g+1)
CompleteIndex(g) -> audit reservation g+1 -> invalidate old Complete -> AuditInProgress(g+1)
AuditInProgress(g) -> success -> CompleteIndex(g)
AuditInProgress(g) -> any normal terminal -> Incomplete(g)
AuditInProgress(g) -> Error／OOME -> non-Complete at g; original throwable propagates
CompleteIndex(g) -> successful permit consume -> CompleteIndexWithActiveLease(g)
CompleteIndexWithActiveLease(g) -> handoff close -> CompleteIndex(g)
any non-lease state at g < Long.MAX_VALUE -> E2 invalidate -> Incomplete(g+1)
any non-lease state at g = Long.MAX_VALUE -> advance request -> GenerationExhausted(Long.MAX_VALUE)
GenerationExhausted -> audit／invalidate -> same GenerationExhausted
any state -> exact server stop／removeServer -> Removed／no map entry
```

Reentrant audit while `AuditInProgress`固定fail fast，generation delta為0且原audit state不變。
未來Complete permit至少綁定exact audit service identity、server object identity、`IndexState`
identity、generation、creation thread、captured tick與unused state。Handoff至少綁定exact
service、server、active-lease state identity、generation、lease identity、creation thread、captured tick與
single iterator state。Generation相等不是充分條件；必須同時驗exact state identity，避免reset／
ABA式誤認。Generation也不是唯一freshness token；Store／journal／source witnesses仍依
既有authority重驗。

Generation lifecycle的first-failure precedence固定為：

```text
1. null／programming／server／thread
2. active lease／reentrant audit invariant
3. index generation reservation
4. generation exhaustion
5. existing P4-E 18-step root／source order from heap floor onward
```

Exhaustion在source work開始前回`Incomplete(GENERATION_EXHAUSTED)`，但不覆蓋較早的
null／wrong-thread／programming invariant。Reservation成功後，後續source／domain first failure
仍依既有18-step順序決定，generation不得改寫其分類。

唯一production startup composition固定為同一`ServerStartingEvent`／same logic-thread call chain：

```text
P4-B Store install
-> P4-D journal bootstrap
-> P4-E1 bounded audit
-> if and only if fresh Complete:
     SkillRetentionRootSnapshot.fromCompleteRoots(raw ordered roots)
     -> require Complete
```

field／index／callback且不跨tick；memory-only index只保存上述internal `CompleteIndex`或
`CompleteIndexWithActiveLease`，不保存public permit或`SkillRetentionRootSnapshot.Complete`。

journal projection都不改Store dirty。E3 reclaim `Rejected`不retry，`Completed(0)`不dirty，
`Completed(>0)`沿用P4-B publication-before-dirty；P4-B invariant failure沿用Unavailable／
`setDirty(false)`。Audit成功本身不dirty也不清掉已有dirty。不得直接呼叫raw
`SkillDefinitionStore.reclaim`、移除missing root後retry、改journal／playerdata／quota、delete
SkillId、promotion到latest或建立第二carrier builder。

  不得保留`PlayerList#getPlayers()` live view、重跑admission或讀同UUID excluded source。
- P4-C full-admission classification與registered serializer等價；missing zero roots，Ready roots，

- Offline defer-to-login保持disk hashes；P4-D recovery → E2 ordering；atomic multi-prune、generation
  MAX、identity drift與一次`setData`。
- Memory-only index restart `Incomplete`，source change／race／reconciliation invalidation、server-stop
  cleanup，無raw／public Complete permit retention。
- Index generation的`NoEntry -> Incomplete`、internal baseline 0、first accepted audit generation 1，
  並分別證明success、`Incomplete`、`OverLimit`、`ReconciliationRequired`都只消耗一次；
  final freshness failure、operational `RuntimeException`不再增加，`Error`／OOME原樣外拋且
  generation留在已reserved值，舊Complete不復活。
- Index generation `Long.MAX_VALUE - 1 -> Long.MAX_VALUE`合法；MAX後的audit或E2 invalidation進
  `GenerationExhausted`、不wrap、清除舊Complete permit authority／backing、source work／root
  capture／Store audit／snapshot／reclaim全為0，repeated exhausted audit／invalidation idempotent且
  只影響exact server slot。
- E2 invalidation只增加generation一次，one reconciliation batch不按pointer數增加；permit
