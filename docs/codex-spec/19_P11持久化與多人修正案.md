## 4. 已接受短期工作、exact A 與因果

### 4.1 Scope、owner 與准入

唯一 gameplay runtime 仍為 P5 SkillRuntimeService；P6仍 Request→Resolve→CommitPlan→ordered Commit，Mana仍唯一 transaction service，P8只觀察 applied fact。任何新 input 必須仍由在線、當前 exact actor/session/native permission admission；「已有 UUID」或 retained recipient不授新 cast。

正常 logout 前已成功 admission、尚未 terminal 的短期工作，得在同一 server instance 繼續 accepted pre-spawn、OPEN 或 claimed-child。正常 logout provenance 必由真 logout/remove cleanup 的具名成功路徑、exact A、server/token及既有工作建立；不能由 `isRemoved`、connection null、同 UUID 或缺在線名單推論。若 cleanup 中途未知／fault，按 §6 分級，不冒充正常 logout。A已被死亡、維度、reload、unload、server stop/restart、原lease/reference條件終止者不能復活。

每個原檢查點——root pre-dispatch、opener、ENTRY/PRECOMMIT/BEFORE_STEP、transfer、claim、next drain、entity/handoff——必须以同一限定 predicate 判斷：原 exact A 綁定仍有效，且是原完整在線資格，或具有上述正常 logout provenance 的已接受工作。原deadline、hit時機、loaded-only、target budget、revision/pin與一次world commit保持；不得為新容量或保存故障延遲命中、少target、減傷或換revision。

P7 disconnect仍停止session/epoch、未受理 intents、pending ingress與未送ACK；此停止不取消已成功交给P5的工作。重連B使用新網路資格，不能重授A；A工作也不因B出現而被改成B施法。

### 4.2 Witness、resolver、native cause

P5 InstanceState保持 accepted pre-spawn唯一 witness custody；原 `RESERVED→OPEN` transfer原子移交给P9 entity。P5-owned continuation permit保持actor-free、P6 retained actor=0；actor只作原call-scoped交付。清理不要求A正常在線。

## 5. 原生source、canonical reward與presence

### 5.1 身份與單一真相

每UUID僅一個P11資料協調owner C／operation scope O；它不是第二個native帳戶、第二scheduler、mana service或definition store。A是工作原因果actor；B是原生正準備／交接的candidate；R是當次合法reward recipient。e為source epoch，v為該source可證的保守dirty/sealed mutation版本，均不能代替material completeness。outer native operation固定R/e；巢狀操作沿真正owning context，不能中途因UUID查到B偷換recipient。

完整性分開判：required material完成、world/roster/listener membership、P4/E2/C/P7 readiness、physical persistence。能serialize、PA有progress、packet送出或B出現在map都不是全部完成。完整B尚未ready可以保資料、接受合法原生credit及保存；partial B不能假whole source。

原attempt owner在第一個受管mutation前，以已取得責任內的預留空間持一份bounded receipt：server/UUID、exact A/B、transition identity、source/load disposition、e/v、具名stage及所需結果。已接受work不因臨時記錄滿額失去credit。至少分開以下material witness：

### 5.4 Canonical PlayerAdvancements reload不得倒退dirty progress

對P11延長生命期的canonical `PlayerAdvancements`，資料包reload必須保留仍適用於新definitions的可信最新progress，不能以較舊JSON覆蓋未成功保存的memory。唯一owner仍是`PlayerList.advancements`中的同一PA；不另造PA、進度Store或reward replay queue。Z `PlayerList.reloadResources`897–899迭代同canonical物件；`PlayerAdvancements.reload`85–95現為stopListening→clear progress/delivery→新tree→load JSON。tracked路徑須將這次reload的進度input改為**當下canonical memory的原生Data表示**，不強迫先成功寫盤才准reload，不在new load之後overlay舊snapshot。

在第一個破壞性clear前，same owner取得可信來源／generation與一份call-scoped完整進度input。`asData`158–165雖建立新map，仍引用可變`AdvancementProgress`，不可視為immutable snapshot；需要跨可再入接點的材料，必須以原生Data／AdvancementProgress codec的受控完整copy固定其值。該材料只是同次reload的input，不是第二可寫truth，真終態後釋放。copy失敗不得clear成empty或改讀舊disk；保可信source，依F1隔離受影響的reload／listener資格、保原錯誤，不報成功。

tracked reload保持以下原生次序與語意：

1. `stopListening`79–82從所有trigger types移除該PA舊listeners。
2. 清舊tree的delivery集合及progress映射，安裝new tree。
3. 依ResourceLocation把完整原生Data對應到new manager，沿`applyFrom`145–155、`startProgress`301–304及`AdvancementProgress.update`55–64更新requirements。新tree不存在的ID沿native告警／忽略；刪除criterion與新增空criterion沿native更新語意，不把舊done欄位當新requirements完成證據，不保留舊listener／definition graph暗中延長已刪內容。這是資料包變更的既有原生語意，不是把本應保留的有效進度退回舊磁碟版本。
4. 保留**這次真正reload**原本會發生的`checkForAutomaticTriggers`103–109及`registerListeners`97–100／220–234，各依本次原生控制流執行一次。不得為重建已有progress呼award／grant；也不得把「避免replay」擴成刪掉原生reload對empty-criteria definition本來就會產生的automatic grant。
5. 同canonical owner保守標記真資料變化及dirty保存責任。client `progressChanged`被flush清掉不表示磁碟dirty已清；只有save的真encode/write/close結果對應相同PA／source／版本，才能清其保存責任，較新mutation仍dirty。

reload、award/revoke、automatic grant及owning command context使用同一scope／generation觀察。native callback同步再入reload時，不得以同main thread推定無再入。每次真正reload的input只在自己的新tree安裝時使用；之後callback造成較新reload，舊外層尾段不得重新apply舊input，或把舊manager listeners登回新tree。listener註冊／終態發布必驗當前tree generation；舊finalizer只收束自己的責任，不重award／grant補差，也不將數次真reload折疊成省略原生新事件。原先已捕獲的native listener/callback按原body與錯誤語意完成，不建立可重播world/reward request。

只有確實需要讀回，且有相符source與成功保存版本證據時，才可選disk。`save()`的void返回或log不證成功；保存失敗時reload不得倒退較舊JSON。資料來源仍由原canonical owner保存，原P5 reload終止規則保持；保PA進度不讓舊flight跨reload復活。

本節direct consumers為Z `PlayerList.reloadResources`897–909；`PlayerAdvancements`fields54–63、`reload`85–95、`load`113–129、`save`131–143、`applyFrom`145–155、`asData`158–165、`award/revoke`168–211、listeners79–82／220–248；`AdvancementProgress.CODEC`25–43及`update`55–64。`SimpleCriterionTrigger.trigger`41–68會先捕獲listener list再依次run；`AdvancementHolder.equals/hashCode`16–30按ID，均不能當作舊call stack已消失或新tree generation相同的證據。source行號指本規範鎖版Z，新增hook／scope與結果觀察仍是待實作能力。

### 5.5 Canonical PA的B初始同步與獨立delivery責任

`PlayerAdvancements.setPlayer(B)`75–77只改recipient欄位，不重建visibility、不保證B得到完整初始進度。正常constructor仍保原setPlayer及callbacks；provisional association本身不等於delivery-ready或cast-ready。

B的真native PLAY connection／Login安裝達到可投遞條件後，在第一次合法`flushDirty(B)`之前，same canonical PA建立本次**recipient/connection generation**的initial-sync責任。原生delivery eligibility與source完整性／P7 readiness分開，不要求P7 Ready才准投遞合法原生同步，也不因listener.player尚在正常交接便全域拒絕prepared B的合法封包。此處只重建client delivery，不重做progress、load、award或grant。

initial-sync須從current canonical progress重新建立delivery狀態：清前recipient的`visible`、`rootsToUpdate`、`progressChanged`及過期selected-tab delivery狀態；以current `AdvancementTree.roots()`105–106填入待重算roots，依原`updateTreeVisibility`306–322建立當前可見definitions，將當前可見progress納入完整包。使用原生`ClientboundUpdateAdvancementsPacket(reset=true, …)`並保持真正native tab處理語意；不可用非reset增量假裝新客戶端已有舊tree。

**零可見進度也必須完成reset。** 原`flushDirty`270只在資料集合非空時send，275卻無條件把`isFirstPacket`設false；所以只setPlayer或只setFirstPacket都不足。tracked initial-sync窄接點必須允許送出空的原生reset=true包，清除同connection舊client tree。client原`ClientAdvancements.update`41–74在reset=true時清tree/progress，60行以`!shouldReset`限制完成toast／telemetry；initial sync不得為重建畫面重播完成提示或遊戲獎勵。

只向本次exact eligible B connection投遞。無eligible client時保留一個有限needs-initial-sync責任，不呼會清delivery集合的無效flush，不保留待重播packet list。建包／send失敗或recipient變更，保原錯誤與未完成責任；之後的合法同步重新取當前canonical狀態建包，不replay舊封包或reward。正常local submission只證提交，不宣稱client ACK或durable save；提交後沿原native dirty增量同步。舊connection／recipient的delivery狀態不得消耗新B的initial-sync責任。

原生advancement初始同步、`ServerRecipeBook.sendInitialRecipeBook`115–116與P7 mana/cooldown fullSync是三個獨立consumer。任何一個完成都不能代證另兩個；它們重送既成狀態，不重新發獎。

direct consumers為Z `PlayerList.getPlayerAdvancements`843–859（同canonicalPA及原setPlayer）、`placeNewPlayer`187–209（native Login、recipes、stats markAllDirty、recipe initial）、`ServerPlayer`530（原flushDirty tick consumer）、`PlayerAdvancements`54–63／75–77／251–289／306–322、`AdvancementTree.roots`105–106、`ClientAdvancements.update`41–74、`ServerRecipeBook.sendInitialRecipeBook`115–116，以及P7自己的正式同步consumer。本節不以單一登入事件代替這些實際交接點。

### 6.3 Source chooser、保存及fault處置

每次入場必先判來源：最新可信完整live source或有完整provenance的immutable材料、真正persisted readback、真正不存在三者不能混同。正常absence只有可證非I/O/parse/error且無已知更新source時才能初始化。已知較新live/failed-save結果存在時，不得回退舊disk再稱latest。讀取、required load、copy及caller必要stage需各有有限receipt；缺一即不能由「能encode」猜完整。

detached A全體native serializer可用，但保持同次正常logout保存接點的Pos/RootVehicle/Brain envelope，不能用removed狀態新算出錯誤登入位置/乘騎材料。qualified B直接serialize其native final state，**不承接A logout envelope**；只有B日後自己完成正常logout才建立B該代envelope，不將A snapshot逐欄overlay B。

必須區分原生保存子scope與額外deferred封存：正常PlayerList.remove的save364在後續unride/stopRiding之前，該原native save接點可形成call-local coherent材料及同次envelope，不要求整個logout Fop先terminal；不得推遲到移除後才取錯資料。額外deferred snapshot則須outer operation/owning Qctx已收束、source身份及版本一致；原保存子scope與deferred都不能收集半A半B。若native保存時有非預期再入、source/material不合格，按真資格阻不可信write，不以無條件save保留宣稱安全。v不是攔截所有未知mod任意欄位的魔法版本；無法證coherence須保source責任而非seal成功。

所有writer須接同qualified-source選擇，沒有旁路：普通player `.dat` writer、logout/autosave/stop；integrated host cached Player data在賦值前；world `level.dat` Player欄位的原world writer；canonical stats、advancements及world各自原owner。host不能先將partial B塞cache再指望後面guard。可保可信既存Player材料，但不能把「這次world存了其他資料」宣稱「新player已保存」。若沒有可信Player材料，共用level.dat replacement可能受阻；chunks/SavedData按各owner，不承諾永遠只影响單UUID。

實際save接受依據是source/e/v、實際write/close/replace boolean、必要readback／worker終態，非SavingEvent、void return、dirty=false或console字句。舊in-flight成功只認exact版本，不清新dirty；obsolete source不得物理覆蓋新source。每physical source只有一writer，無跨檔atomic承諾。

### 6.4 P4 provenance 與 sole continuation

P4§17清journal仍只認原契約later **persisted readback**：persisted base保留／intermediate只清已證prefix再replay suffix／final才完成clear。matching RAM handoff即使值等於journal target亦非此proof；save嘗試／void返回不能升格。最新合法volatile publication可由ordinary submission、recovery或E2產生，不限recovery receipt；它可接續資料，但不能藉此清journal。

已證live publication合法且仍current者只接續，不重setData或replay同一installed target。只有RAM恰等target但無provenance，既不能清journal，也不能一律再setData；該未證狀態保持隔離並由sole owner查明。其他正常P4 chains/recovery仍依原規則進行，不能為避免clear把整個recovery跳過。

`SkillSubmissionRecoveryService`仍唯一LoggedIn recovery owner，`P4E2OnlineReconciliationCoordinator`仍唯一reconciliation/login-ready owner。對完整B只欠metadata的已定位failure，新增private、typed、bounded continuation receipt，綁exact B/source e、exact connection、P4 state及最新publication provenance、Attachment identity、原失敗stage及已完成E2/C/P7 session/initial-sync步驟。只有證據表明某stage未做，才由**同owner**補該stage；原consume-first handle已消費不能再consume，不重setData、clone/load、recovery whole-chain或open已有session；已開session只能補可證缺失的initial sync，不另加login listener/下一tick通用recovery。

metadata完成、data完整、durable、可cast各自驗；source已換、receipt缺失、未知mutation、原Exception/Error未解不當Ready。斷線後是fresh login及新驗證，不由client STATUS觸發resume。若同場景repair需要operator原因，經既有owner的具名private入口並記原因，不能自造公共救援權限。P4 Raw/marker可局部隔離技能；只有whole-source不可信才拒入世界。

## 8. 首個 TRY 未受理分支的完整修補

### 8.1 精確替換正文

本節採用AP§8對TR初始TRY條件缺口的完整修補，規範以本節為準：STATUS不推動gameplay/native/P4/E2，只讀bounded現況及本節未受理控制終結；保護所有保留位置；BINDING按本文件§7.5。此來源修補不是已重現deadlock的runtime證據。

**STATUS(n)只可在以下全部成立時建立NOT_STARTED(n)：**

1. 固定schema、合法command/kind/scope、exact connectionEpoch/sceneSerial/actorGeneration、phase及original/expected actor規則全部通過；舊scene先失效才可讀寫current/fence。查詢不能建scene、選actor、授permission或改native條件。
2. n為合法positive client sequence且大於適用current/fence；有下列之一：**可信新scene**由正規PLAY DEATH/END publication建立、owner從建立起明存從未受理actor attempt來源，無server-issued attempt/mutation/未知交接；或**前次已結清**current到原契約允許同scene新意圖的terminal且無未解stage／交接。空current/log、UI timeout、receipt遺失均不構成證據。不可覆蓋仍需保留的COMPLETED/frame、FAULT、UNKNOWN、closed、EXPIRED。
3. 同connection owner、同ingress/main線性化邊界，核實沒有**任何**需保留TRY：包括inbox、已取出未進body的drain reservation、admission/executing、current attempt及CONFIG→PREPLAY／parking→game必要handoff。即使保留的是m≠n也不可替換／越過。
4. 所有可到native body的工作始終由上述有限位置代表；inbox→drain→current與phase交接原子移交責任，不先清舊後補新造成空窗。延後drain執行前重驗exact owner/listener/phase，真正admission在body前重驗current/fence。

成立時，同一線性化操作記`current=NOT_STARTED(n)`、拒n及更舊seq的fence、增加statusVersion，然後才發布。所有晚到／重送／已排未取得執行權的TRY(k≤n)均不得body。可由既有current.requestSeq表示fence，必要獨立scalar亦僅一份有界欄位，無歷史map。不得先通知再裝fence。

此操作不進native body、不建B、不取得執行H、不呼P4/E2 resume、不完成config task、不更動真正eligibility。只有保有對n的具體限流證據才用CONTROL_RATE_LIMIT；aggregate counter不能證n；其餘已證未受理用CONTROL_DISPATCH_BUSY。

n在保留位置則保PENDING/原結果；其他m在保留位置亦保m，對n只能合法bounded現況／UNKNOWN／等待，不更新fence越過m。RUNNING/frame、不明mutation、遺失receipt、未解stage不得回退NOT_STARTED。發送失敗不抹record；未收到回應不是沒做。

每connection一inbox＋至多一queued/executing drain；TRY可替換純STATUS，STATUS不得覆蓋任何已收TRY。移出inbox後保護仍在；duplicate可合併，違規pipeline不加queue／per-packet Runnable。native callback nested pump時不得重入同owner第二drain。STATUS及latest通知coalesce並有限公平處理。

原條件／配額解除後只通知MAY_TRY；玩家neutral/release後新操作取得下一合法connection seq，不aut replay、不假設第一n=1、不因scene/phase/P7/UI重設counter。BINDING0只發布scene；JOIN/RETURN/ENTER_CONFIG的server request0自task/caller開始即保存真正PENDING/attempt/stage，不套用fresh DEATH/END空白分支。

phase推進保scene/current/fence/status/provenance；listener retire不消失交接receipt。expected B保原A或actorless request至matching frame＋caller terminal。舊query不能封新scene；counter/status耗盡停止新admission，不wrap；late結果不逆phase或重開UI。

## 10. C6 啟動配置、分層資源及保存負載

### 10.1 唯一配置owner與根責任

擴充現有 `P5ServerRuntimeConfig/P5RawServerConfigSpec` 的同一SERVER spec `gramarye-server.toml`，在Gramarye原server-start composition接點產生獨立immutable P11 limits；不另註冊競爭spec、不改原P5 16 keys/defaults/關係。新service發布RUNNING前完成整體驗證。runtime不持raw/provider/history/reload callback；檔案改動只影響下次server slot。非法/缺值/錯型/overflow/關係矛盾具名報key與closed reason，使本次P11啟用／啟動明確失敗，不clamp、不無界fallback、不默填診斷profile。

### 10.3 公平control與bounded I/O

每connection一inbox、一queued membership/drain及一latest通知；sole dispatcher有圓形cursor，服務一owner就前移，新arrival排在已等者後，不持續搶隊首。owner內inbox與通知有限交替，任何一邊不永久飢餓。TRY可換純STATUS，STATUS/另一不同TRY不覆蓋已收TRY；移交遵§8。

若有C個持續eligible owner、每tick完成q≥1 quantum且無native長阻塞，一輪首次服務界限為`ceil(C/q)`個**可服務tick**；不是永久overload也必回覆。count budget不暫停已開始native transition、不延遲已受理world hit。active native connections與waiting分列，不能把P7 sessions256當全部control connections cap。這是原control dispatcher公平policy，不是第二gameplay scheduler。

封存身份至少source-kind/UUID/e/v/actor-load disposition，bytes與source receipt分離。額外deferred封存只在main且outer native operation/Qctx完成、source/coherence可證時作；原native save子scope依§6.3在其合法call-local接點serialize，尤其logout envelope不延後到unride之後。收集deepcopy中e/v/scope改變不得seal。worker不得讀actor/world/Attachment或發event。

bytes固定定義為該完整immutable NBT以Z `NbtIo.writeUnnamedTag`167–172 framing的**未壓縮logical serialized width**（tag-id＋empty root-name＋payload），不是compressed檔案大小、Java retained heap或估算字串length。合法main接點原serializer先形成coherent root；對該root作同framing的strict bounded traversal/count，至remaining+1即停止，不再呼entity/Attachment serializer、不分配等長byte array、不走帶log/空字串fallback的StringFallbackDataOutput。可計數且額度足夠，才在同owner原子reserve count/bytes再額外deepcopy/seal；copy/coherence失敗放回reservation、保dirty與真fault。超budget或不能在此strict座標封存只表示不能新增這份deferred材料，不把native既有資料判非法；合法原native保存仍按§6.3與下段進行。原root/serializer暫存峰值明列在budget之外，不能據此宣稱heap有硬上界。

未開始舊snapshot僅在同source新coherent snapshot完整取代其狀態且不負journal/readback/transition材料時可合併；epoch不同不可任意合併。journal、event、reward、queue continuation、incident材料不是可任丟的snapshot。舊in-flight完成不得清新dirty。physical replace前仍由原writer驗source/version；「main批准、worker稍後replace」若期間可publication新source就有obsolete-write gap，首版保replace在原main writer，不靠completion callback才發現。I/O重試只寫資料，不重副作用。

Z PlayerDataStorage.save33–45無whole-player byte cap，load61–71使用NbtAccounter.unlimitedHeap。P4 Attachment16MiB／audit256MiB或queue budget**都不是native合法whole-player上界**。maxSealedBytes不足時不新增複製／排隊，以原native同步writer保存可保存資料並保receipt；不能讓正常save永久因queue cap失效。此native serializer暫存峰值不受queue cap保證；若具名整合不能提供這條路，須在啟用依賴能力前補此窄缺口，不能降低R1。全player讀取成本是部署量測限制，不造新未批資料cap。

## 11. 正式冷卻基礎能力

### 11.1 正式政策producer、資料版本與profile

本節是正式production資料／執行能力的after-set，不是新上市技能。唯一policy producer在server main，以exact authenticated owner、已核驗equipped `SkillReference`及P5已取得並pin的immutable validated exact revision為輸入，從node0的typed `active_cast`產出`Zero(D=0)`、`Positive(policy_version=1,D)`或`Unavailable`。不從client數值、slot名稱、latest template、test SkillId或global override產生D。Unavailable不能default0；當前definition不可用不能洗掉同SkillId已有義務。

### 11.2 唯一owner、准入與zero

獨立Attachment ID為`gramarye:cast_cooldowns`。唯一registration仍是`PlayerSkillAttachments`的DeferredRegister，沿既有closed definition-only bridge供跨package註冊；不加第二registry owner、不暴露任意mutator/service locator。唯一cooldown service持immutable Attachment真相，cell身份為server identity＋authenticated UUID，entry key為SkillId。資料協調C只協調native保存／來源，不另持一份冷卻帳；P5 receipt只是attempt事實；P7只投射。

只有真正不存在且無I/O／parse錯誤、無已知較新live/failed-save source時才可初始化；可信legacy player資料缺此尚未部署的cooldown key亦可初始化。Unknown不是absence；外層來源不完整先按§6阻止不可信world admission。unbound load/clone carrier僅是immutable材料，沒有cast/mutation權；canonical binding及單writer才成真相。

### 11.3 PREPARED、PENDING與真正ARM

正D須在同一P5 owner把現有acquireAndPublishRoot拆成不可執行prepared ticket：pure checks／quota／lease／actor／exact ref→捕獲Ga/Ra/rootDeadlineR/D/attempt並預建immutable replacement→cooldown cell按expected generation裝PENDING→exact root publication→Accepted。同call收束ticket；不是先Accepted再blind cancel作rollback。prepare／typed reject不新增義務；已裝PENDING只能由exact no-publication或不可逆NO_RELEASE清除；publication unknown→UNCERTAIN，不重publish。

native add前entity處於`PREPARED_SPAWN`；包括同步再入的tick/onHit/claim，ARM前均不得產生Gramarye gameplay effect。native add依原時序執行，可能先發join/tracking/ticking callbacks；true不等可用釋放，false/throw不證原生外部副作用0，不回滾原event。

native add返回後，在同call重驗entity alive/added、exact entity/level、token/generation/epoch/ref/lease、runtime/reload、可信clock及bound。P5唯一owner正式發布OPEN的**單調ARM receipt**才構成release，無額外tick等待。ACTIVE replacement預建；最後短段不任意callback、I/O或診斷分配。receipt前對外只能觀察PENDING或不可序列化staged值，read/serialize必查receipt，不得在install ACTIVE與OPEN之間暴露假release。這不是承諾跨owner或VM原子transaction。

receipt必先轉入唯一cooldown cell再回收；後來permit CLOSED仍不能抹去曾ARM。NO_RELEASE必須同時證明從未ARM且原attempt已不可逆失去未來ARM資格，不能只看現在非OPEN。跨RuntimeException／Error用exact receipt收束可證狀態並保原primary/error語意，不catch-and-continue世界工作；无法判定保UNCERTAIN，不重spawn/hurt。

| 事實 | 義務／非義務結果 |
|---|---|
| native false、callback移除後true、確定transfer拒絕，且已不可逆撤銷ARM | NO_RELEASE，不收正式D；原生已發生副作用如實保留。 |
| ARM r已可證 | ACTIVE expires=r+D；miss、shield/protection、hurt=false、target gone、P8或ACK失敗均不退款。 |
| ARM後world work terminal | 只結束world work，冷卻仍到原expiry。 |
| 正常logout | accepted work及既有PENDING/ACTIVE由原O/owner承接，不重新起算。 |
| reload／normal stop，尚未ARM且可證撤銷 | 清義務再由qualified source final save；ARM後保ACTIVE；unknown不清。 |
| restart | 只恢復資料義務，不復活P5 work/projectile。 |

### 11.4 捕獲上界、時計及已接受的恢復條件

採Overworld `gameTime` G，不用client tick、wall-clock或command可改的dayTime。Ra為admission當時P5 runtime tick；Ga為同一受控時點G。以checked arithmetic捕獲：

```text
release_not_after = Ga + (rootDeadlineR - Ra)
U = release_not_after + capturedDuration
本closed profile：rootDeadlineR - Ra = 101
ARM必要條件：可信 G <= release_not_after 且 R < rootDeadlineR
```

來源是本基底`SkillRuntimeService`179–185的delay0／horizon100、1157–1172的base Ra+1及deadline Ra+101；原projectile ARM的strict截止與一般event的終止比較不得混同。P5 Post tick遞增見1475–1504／2922–2927；Z `MinecraftServer`912–943／1024–1043、`ServerLevel`337–360／441–445支持正常server loop中G每runtime tick最多增1的推導。這是鎖版正常時間流程下的bound，不普遍套未來任意profile或第三方直接gameTime跳轉。

publish前拒overflow／不可表示U；ARM超bound取消或clockUnavailable，不事後延長。clock_floor是已可信觀測G的高水位；now<floor先CLOCK_UNAVAILABLE，不以max(now,floor)掩飾回退／降floor。gameTime暫停只令經過時間變慢；正常關服不補wall-clock。read/clone/relogin不重新捕獲now+101，candidate pair不是release證據。

### 11.5 Exact reconciliation與保存失敗

同JVM先查同attempt及generation的exact publication／NO_RELEASE／ARM事實，由sole cell CAS單次轉換。known ARM一律用真r+D；known irreversible NO_RELEASE清除；不因單純保存失敗降UNKNOWN。只有真正未知且policy/route/bound/clock全部可信才套以下恢復：

| 可用證據 | 恢復 |
|---|---|
| orphan PENDING無live token，或UNCERTAIN knowledge0 | G<U為RECOVERY_PENDING_BOUND；G≥U可證所有可能合法義務均到期，prune。knowledge0有candidate pair也不能提前依candidate expiry清。 |
| UNCERTAIN knowledge1且合法ARM pair | 還原真ACTIVE／exact expiry，不等U。 |
| future/malformed/bad route/bad bound/policy/clock | quarantine／unavailable；沒有有限恢復保證，不套「所有錯誤101ticks」。 |
| exact ACTIVE只保存失敗 | memory保ACTIVE＋真expiry，另記durability failure；不造UNKNOWN。 |
| NO_RELEASE已clear但write失敗 | 同JVM較新clear勝舊disk PENDING；必要durability gate顯SAVE_FAILED，不冒充仍冷卻。crash丟RAM後只能按真disk PENDING恢復。 |

首次PENDING從未持久就crash的缺口不具此readback恢復保證，不宣稱VM跨owner原子或絕不漏義務。資料重試只寫資料，不重副作用。normal clone採原Attachment copy語意及same current truth，不從disk混合或overlay；正常重連先qualified source後一次load；clock_floor及attempt/bound保持。

工程算例（不是技能預設）：Ga1000、D120→bound1101、U1221。若ARM1002，真expiry1122，但disk只有PENDING時可保守到1221，額外99，對確實已ARM的合法義務最坏額外≤101。若其實未釋放而取消未落盤，disk只知PENDING，可能等待101+D；不能稱它只是「實際冷卻多101」。這兩分支及known receipt優先須分開驗收。

### 11.7 實際bytes/depth與保存座標

冷卻bounds是post-materialization logical tree座標，不是compressed file、whole-player、Java heap或pre-allocation/OOM防護。logical Compound已物化前的physical duplicate tag bytes不在此round-trip保證內。local raw深度≤8，whole raw≤16，final preservation wrapper≤17；root tag depth1，container child+1，normal最大depth4。copy前strict計數，至limit+1即停。

ASCII字段計算：anyTag=1(type)+payload；named field=3+name.length+payload；Compound END=1；List header=5；UUID IntArray payload=20。共同named fields為31+8+15+21+21+22+33+28=179。
