## 2. SkillRevision

### 舊規則

`SkillRevision` 使用非負 `long`。

### 新規則

```java
record SkillRevision(int value)
```

- 合法範圍為 `0..Integer.MAX_VALUE`。
- Canonical JSON 是普通非負整數，不編碼為字串。
- P3-C 只依 authoritative snapshot 提出 candidate revision，並在 latest 為 `Integer.MAX_VALUE` 時形成既有的 `RevisionExhausted` preparation outcome；P3-D 只有在 atomic compare-and-insert 成功時才正式配置 revision。
- P3-D1 additive 建立唯一 `SkillRevision.successor()`，建議回傳 `Optional<SkillRevision>`；非 MAX 回傳 `value + 1`，MAX 回傳 empty。P3-C3 proposer 與 P3-D2 commit arithmetic 必須共同使用此 operation，它不表示正式 allocation。
- 合法 `SkillSubmissionPlan` 不可能攜帶 `ExpectedLatest(MAX)`，因此正常 Store commit result 不含 `RevisionExhausted`；Plan 建立後 actual latest 若前進至 MAX，依 CAS precedence 回 `LatestMismatch`。違反此 Plan 不變量是 programming misuse。
- 不得 overflow、wrap 或重用過去的 revision。

### 理由與相容性

在首次正式 `SkillDocument` schema 建立前將範圍固定為跨 JSON、NBT 與未來網路層都可直接表達的有界整數。P0～P2 尚無正式技能文件持久化資料，因此不需要 migration；P1 的 Java record、Codec 與測試由 P3-A 同步修改。

## 3. 正式文件模型與 Node 身分

### 舊規則

舊示意模型以 `SkillDefinition` 持久化 resolved／unknown definition union，並在 `NodeDefinition` 儲存一份 `index`。

### 新規則

```text
SkillDocument
├─ schemaVersion
├─ SkillId
├─ SkillRevision
├─ ordered List<NodeDocument>
└─ AppearanceDocument

NodeDocument
├─ DefinitionEnvelope trigger
├─ DefinitionEnvelope action
└─ AppearanceOverrideDocument
```

- `SkillDocument` 是固定 revision 的唯一持久化文件真相。
- `NodeDocument` 不儲存 `index`；List position 是該 revision 內唯一的 `nodeIndex` 真相。
- persistence 與 runtime 使用零起算 index，UI 顯示 `index + 1`。
- Node reference 只能指向較小 index，由 P3-B 驗證。
- P3 不建立 `NodeId`。
- 未來 `SourceContext.rootNodeId` 更名為 `rootNodeIndex`。
- 存在 Unknown classification 時，編輯器不得進行無法安全更新隱藏 Node reference 的重排。

此決定移除舊 `NodeDefinition(int index, ...)` 的第二份 index 真相。

## 4. Envelope、resolution 與 runtime projection

`SkillDocument` 的 Trigger／Action 欄位始終只持久化 `DefinitionEnvelope`；不直接持久化 `ResolvedTriggerDefinition`、`UnknownTriggerDefinition`、`ResolvedActionDefinition` 或 `UnknownActionDefinition`。

P3-B 流程固定為：

```text
SkillDocument 中的 DefinitionEnvelope
→ registry resolution
→ transient resolved/unknown candidate
→ validation
→ ValidatedSkillDefinition
```

- Unknown／Resolved 是 transient classification。
- 原始 Envelope 始終保留在 `SkillDocument`。
- `ValidatedSkillDefinition` 是可由文件重建的 runtime projection，不是第二份持久化真相。
- 不建立讓 `SkillDocument` 與 `ValidatedSkillDefinition` 同時實作的寬鬆 `SkillDefinition` runtime 介面。

P2 的 `DefinitionEnvelope`、descriptor registry、resolved／unknown definition Codec 與 raw snapshot API 不需 migration 或修改；P3-B 使用它們作為 transient resolution 邊界。

## 5. Appearance partial schema 與 Profile 三態

Appearance 是部分覆寫模型；任一欄位缺失都表示 Inherit。僅指定顏色或 intensity 合法，非空 Appearance 不必同時提供 sound、particle 或 trail。

- top-level `appearance` 缺失、`null` 或 `{}` 都 decode 為 Default；canonical encoding 必須寫出 `{}`。
- Node `appearance_override` 缺失或 `null` 都 decode 為 None；canonical encoding 省略欄位。

sound、particle 與 trail Profile 欄位採 tagged 三態：

```text
欄位缺失                         → Inherit
{"mode":"disabled"}              → Disabled
{"mode":"specified","id":"namespace:path"} → Specified
```

Canonical schema 不使用 JSON `null` 表達 Disabled。寬鬆 JSON decoder 可接受 `null` 為 Disabled，但重新編碼必須寫成 tagged Disabled。Missing、Disabled 與 Specified 在 JsonOps、NbtOps 以及兩者轉換間必須保持語意；不得以單純 `optionalFieldOf(ResourceLocation.CODEC)` 代替三態。

## 6. Appearance tolerant decode 與 raw isolation

Appearance 解碼狀態：

```text
欄位合法
→ Decoded

可由寬鬆規則正規化
→ Decoded canonical value

可辨識數值越界，且具有明確合法區間
→ clamp 至 hard boundary
→ Decoded
→ P3-B transient bounded warning

結構、型別或無法可靠解釋的值錯誤
→ 整個 blob 成為 Unparsed
→ 在 quarantine hard bounds 內保存完整 raw snapshot

raw subtree 超過 quarantine hard bounds
→ Rejected
→ 不保存超限 raw tree
```

Clamp 適用於型別正確、範圍明確的數值，例如 `intensity_milli < 0` 或超過 `MAX_APPEARANCE_INTENSITY`。

Unparsed 適用於 ARGB 無法解析、ARGB numeric 超出 bit-pattern 範圍、Profile mode 未知、Disabled 帶 `id`、Specified 缺 `id`、欄位型別錯誤或其他無法可靠解釋的結構。任一此類錯誤使整個 blob 進入 Unparsed，不保留部分 typed result。

為保持既有向前相容政策，未知 appearance 欄位忽略；「其他結構錯誤」指已知欄位的不可解釋結構，不包含單純的未知欄位。

Rejected 只用於 appearance raw subtree 超過 quarantine hard depth 或 node count。Decoded、Unparsed 與 Rejected 都不得使 gameplay `SkillDocument` 失效或阻止施放；presentation 使用 fallback。

Unparsed raw snapshot 必須與 P2 `DefinitionEnvelope` 具有同等 alias isolation：建構與存取都不暴露內部 mutable tree，不使用 `toString()`、跨 JsonOps／NbtOps 往返或 same-ops `Dynamic#convert` 偽裝 deep copy。

## 6-A. P3-A 實作澄清

凍結規格的數值 clamp 依欄位語意適用：

```text
純量且具有有序合法區間的欄位
→ 可 clamp

位元模式或離散識別欄位
→ 不以數值邊界取代原意
→ 無法解析時 whole-blob Unparsed
```

- `intensity_milli` 是具有有序區間的純量；型別正確且可精確解讀為整數時，低於 0 clamp 為 0，高於 `MAX_APPEARANCE_INTENSITY` clamp 為 hard maximum。
- ARGB 是 32-bit bit-pattern，不具有可用最近邊界代替的連續量值語意；無法解析或 numeric 超出可表示 bit-pattern 範圍時不 clamp，而是 whole-blob Unparsed。
- Profile mode 與 Profile ID 是離散識別資料，不 clamp；不可靠解釋時是 whole-blob Unparsed。
- P3-A 使用非持久化、有界的 read report 保存 intensity clamp、legacy `null` normalization 與未知 appearance 欄位忽略等 provenance facts。`MAX_READ_REPORT_FACTS = 1024`；達上限後停止新增 fact 並設定 `truncated = true`，不使讀取失敗。
- Read facts 只含有界 machine-readable code、location kind、optional node index 與 optional known appearance field；不含人類字串、raw tree、未知欄位名稱或 exception stack。Facts 不參與文件 equality，不由 Storage Writer 持久化。
- P3-B 將 P3-A read facts 轉為 bounded warning；P3-A 不建立 `ValidationIssue` 或 gameplay validation report。
- 未知 appearance 欄位在 tolerant read 時忽略，read report 只記錄 `UNKNOWN_APPEARANCE_FIELD_IGNORED` 而不保存欄位名稱；canonical Storage Writer 會剝除該欄位。若新欄位必須跨舊版 round-trip 保留，必須提升 skill-level schema version 並由 P3-B 定義 migration／forward-compatibility 政策。

## 7. Bounds 與座標系

Hard ceilings：

```text
MAX_UNPARSED_APPEARANCE_DEPTH = 32
MAX_UNPARSED_APPEARANCE_NODES = 1024
MAX_SKILL_DOCUMENT_BYTES = 1 MiB
MAX_SKILL_DOCUMENT_DEPTH = 64
```

Policy defaults：

```text
DEFAULT_UNPARSED_APPEARANCE_DEPTH = 16
DEFAULT_UNPARSED_APPEARANCE_NODES = 256
DEFAULT_SKILL_DOCUMENT_BYTES = 256 KiB
DEFAULT_SKILL_DOCUMENT_DEPTH = 32
```

P3-D Store hard ceilings：

```text
MAX_COMMITTED_SKILLS_PER_OWNER = 256
MAX_COMMITTED_SKILLS_GLOBAL = 4096
MAX_RETAINED_REVISIONS_PER_SKILL = 128
MAX_RETAINED_REVISIONS_GLOBAL = 32768
MAX_RETENTION_ROOTS_PER_RECLAIM = 65536
```

- 上述數值是不可由 config 提高的 technical hard ceilings；後續 Java 實作放入既有 `MagicSafetyCeilings` 或其唯一 canonical hard-limit 位置，不建立平行常數。
- per-owner／global skill ceiling 限制 active Store histories；per-skill／global revision ceiling 限制目前 retained `SkillDocument` entries，不限制歷史上曾配置的最大 revision 值。
- 一次 reclaim 的 complete external root 集合超過 `MAX_RETENTION_ROOTS_PER_RECLAIM`、遭截斷或不完整時 fail closed，整輪不執行 sweep。
- 這些 count proxy 不能取代 encoded-byte bounds。P4 開始 Java 實作前必須先完成 P4-0，固定 whole Store snapshot、per-history、load-time raw／quarantine byte ceilings 與 family-tagged raw storage envelope；P3-D 不得為量測 bytes 呼叫 Codec 或 Writer。

- Appearance relative depth 從 appearance／override subtree root 以 1 起算。
- SkillDocument global depth 從 document root 以 1 起算；兩套 depth 獨立。
- Appearance 超 hard depth／node count 為 Rejected；超 policy 但未超 hard 由 P3-B 產生 WARNING。
- SkillDocument 超 global hard depth 為 document decode error。
- Byte limit 只在真正持有 raw bytes 的 I/O 邊界執行；不得以 `toString().length()` 模擬 byte size。
- P3-A 的 depth／node traversal 是 post-parse tree proxy，必須 short-circuit，不等同 parser-level 保護。

## 8. Draft 決議

- `SkillDraft` 是業務上可編輯、Java instance 上不可變的 snapshot。
- top-level appearance 直接使用 `AppearanceDocument`，不建立 `DraftAppearance`。
- Draft Node 使用 `AppearanceOverrideDocument`。
- P3-A 建立 Draft Codec，明確保存 Missing／Present Trigger 與 Action slot。
- Draft 持有候選 `SkillId`，但不擁有鑄造權。P3-C 定義 server-side SkillId mint contract 與 authoritative submission precheck input；client 不得鑄造正式 SkillId。
- server mint 產生的 transient grant 只供目前 server-side editing context 使用，不是跨伺服器重啟的 submission credential。提交授權必須使用當下的 authoritative snapshot。
- P3-A 不建立 random UUID production factory。
- Draft 的 optional `baseRevision` 只是 optimistic concurrency metadata，不是正式 revision。

## 9-A. P3-C submission preparation 與 P3-D commit 邊界

P3-C 只準備提交，不寫入 Store，也不配置正式 revision：

```text
SkillDraft
→ Draft formalization
→ server-authoritative identity／state precheck
→ optimistic-concurrency／exhaustion precheck
→ proposed SkillRevision
→ transient SkillDocument
→ existing resolution／validation／projection
→ immutable SkillSubmissionPlan
```

- `SkillSubmissionPlan` 必須攜帶 owner／principal、compare-and-insert precondition、proposed `SkillDocument` 與已驗證的 `ValidatedSkillDefinition`。Prepared plan 不等於 committed revision，不得持久化或長期重用。
- P3-C 的 revision 只是 proposal。正式 allocation 只發生在 P3-D 對 Store 目前狀態執行 atomic compare-and-insert 成功時。
- allocation 使用的 latest truth 是 Store 中該 `SkillId` 已存在的最大 revision；玩家 Attachment 的 latest pointer 只是玩家引用，不是 allocator truth。
- composition 在 P3-D commit 前必須重新取得 ownership authorization 與 immutable quota snapshot；Store 在同一 domain mutation 內重新確認 committed owner binding 與 precondition state。state 不符時回傳 machine-readable commit result，不得猜測、覆寫或自動重試。
- P3-D 完成後，由 composition facade `SkillDefinitionSubmissionService` 取得 authoritative identity／state snapshot、呼叫 P3-C prepare，再呼叫 P3-D commit。P3-C、P3-D domain API 都不得依賴 Minecraft `Player`／`ServerPlayer`。
- identity rejection 不得透露未授權 SkillId 是否存在、latest revision 或 owner。server-side transient mint grant 不得取代提交當下的 authorization。

Submission short-circuit 順序固定為：

```text
Draft read warnings
→ draft schema
→ authorization
→ optimistic concurrency／revision exhaustion
→ Draft completeness
→ existing P3-B2／P3-B3 pipeline
```

- Draft read warnings、completeness issues 與 B3 report 使用單一 bounded `ValidationResult`，依上述 stage order 保留 deterministic insertion order。
- 合併 report 時，先逐項把 retained issues 加入 receiving `ValidationCollector`，再以 `inheritReportState` 傳播來源的 `truncated` 與 `omittedError`；不得只複製 retained issues 後宣稱 hidden error 已傳播。
- `Prepared` report 必須 warning-only；`Conflict`、`IdentityRejected` 與 `RevisionExhausted` 也只能攜帶在 short-circuit 前已收集的 warning-only report。Draft 或 B3 ERROR 一律形成 Invalid，不形成 plan。
- P4 將 P3-D Store adapter 與玩家 Attachment 接入不同持久化位置；兩者更新不是天然跨位置原子操作。P4 必須另定 ordering、failure recovery 與 reconciliation，不得宣稱資料庫式全面 transaction。

## 9-B. P3-D0 Store truth、thread confinement 與 persistence seam

P3-D production domain truth 固定為：

```text
SkillDefinitionStore
└─ SkillId → active StoredSkillHistory

StoredSkillHistory
├─ immutable SkillOwnerId owner
└─ immutable retained revisions
   └─ SkillRevision → SkillDocument
```

- owner binding 與 retained `SkillDocument` entries 是唯一 Store domain truth；`SkillDocument` 是 revision 內容的唯一真相。
- committed document 不得覆寫或修改。Store 不保存 `ValidatedSkillDefinition`、`SkillSubmissionPlan`、`SkillSubmissionOutcome`、`ValidationResult` 或 `SkillDraft`。
- latest 由 retained revision keys 的最大值推導。`latestBySkillId`、`skillsByOwner`、owner skill count、allocation counter 與 revision-count cache 都只能是可重建資料；P3-D1／D2 第一版不建立這些 indices。
- 玩家 Attachment pointer 不是 Store owner 或 latest truth，也不參與 allocator 裁決。

`SkillDefinitionStore` 由 server logic thread confinement 使用：

- P3-D 不承諾任意 Java threads 間 linearizability，不使用 lock／`synchronized`，也不依賴 Minecraft thread API 主動驗證 caller thread；thread misuse 是 programming-contract violation。
- atomic Store mutation 表示單次 aggregate method 先完成全部 typed-failure checks，第一個 truth mutation 前 observable state 不變；typed failure 時 owner／history 完全不變。
- 成功時 owner binding、quota admission、CAS、capacity 與 revision insert 共同成立。完整 replacement history 建立後，才做一次 outer-map insert／replace；mutation 後不呼叫會正常失敗的外部 callback。
- 不承諾 OOME、VM `Error` 或任意 `Error` 的 rollback；不宣稱資料庫 transaction 或 Store／Attachment 跨位置原子性。

P3-D 提供 detached immutable persistence snapshot，只包含 active SkillId、owner 與 retained `SkillDocument` entries。Snapshot 是 point-in-time export，不是第二真相，不暴露 mutable internal Map；restore 必須重新驗證 route／document identity 與 hard ceilings。

P3-D 不建立 Store Codec、NBT、DynamicOps、SavedData 或 `setDirty()`。P4 adapter 在同一 logic-thread call 中委派 aggregate；commit 成功後才 `setDirty()`，typed failure 不 `setDirty()`。`SkillOwnerId` 在 P3-C 與 P3-D 都不新增 Codec／StreamCodec／String representation；P4 persistence 才 additive 建立唯一 canonical UUID Codec。

## 9-C. P3-D0 quota、capacity、CAS 與 commit result

Quota model 固定為：

```text
SkillQuota
├─ Unlimited
└─ Limited(maxCommittedSkills)
```

- `Unlimited` 表示沒有額外 per-owner policy quota，不得突破 technical hard ceilings。
- `Limited.maxCommittedSkills` 合法範圍是 `0..MAX_COMMITTED_SKILLS_PER_OWNER`；0 表示不能建立新 SkillId。
- quota 計算每 owner 的 distinct active committed SkillId／owner binding 數，不計 revision、Attachment pointer、Draft 或 pin。
- New 成功增加 1；Existing 新 revision、failed commit 與 old revision reclaim 都不改變此數。Quota 只在已確認真正 absent 的 `ExpectedAbsent` branch 檢查；Existing 不因 policy quota降低而被拒絕。
- composition 在 fresh authorization 後取得 immutable quota snapshot；Store mutation 內不重新呼叫 provider。
- 第一版在正式 retire／delete operation 出現前，預設 policy quota 為 `Unlimited`。主動設定 `Limited` 的伺服器必須接受目前沒有 quota release workflow。

Authoritative quota、owner binding check、`ExpectedAbsent`／`ExpectedLatest` CAS、technical capacity checks 與 revision insert 必須位於同一 Store domain mutation。Quota／capacity／CAS／owner failure 都不得插入 revision或修改任何 count；insert 成功後不得回 quota rejection。

Technical capacity 使用獨立 vocabulary：

```text
SkillStoreCapacityScope
├─ OWNER_SKILL_HISTORIES
├─ GLOBAL_SKILL_HISTORIES
├─ SKILL_RETAINED_REVISIONS
└─ GLOBAL_RETAINED_REVISIONS

CapacityRejected(scope, current, maximum)
```

`current`／`maximum` 非負且 `current >= maximum`；metadata 不含任意 message。Policy quota 使用 `QuotaRejected`，不得與 technical capacity 共用 variant。

每個 active committed SkillId 恰有一個 immutable owner：New 在全部 admission check 成功後以同一 replacement 建立 owner binding 與 revision 0；Existing 的 stored owner 必須等於 Plan owner，且 submission 不得轉移 owner。Mismatch 回 `OwnerRejected(SkillId)`，不保存 actual owner 或 observed latest；composition 對外映射為 opaque authorization rejection。未來 ownership transfer 必須是獨立 Store operation。

CAS precedence 固定為：

```text
ExpectedAbsent:
programming invariants
→ history present: ExpectedAbsentButPresent
→ per-owner history capacity
→ global history capacity
→ policy quota
→ global retained-revision capacity
→ build replacement
→ single insert

ExpectedLatest:
programming invariants
→ history absent: ExpectedLatestButAbsent
→ owner mismatch: OwnerRejected
→ actual latest mismatch: LatestMismatch(expected, observed)
→ successor/proposed-revision invariant
→ per-skill retained-revision capacity
→ global retained-revision capacity
→ build replacement
→ single replace
```

Owner mismatch 必須先於 latest mismatch，避免向不匹配 owner 洩漏 observed latest。合法 Plan 不會進入 commit-time exhaustion：P3-C3 已拒絕 Existing(MAX)；Plan 建立後 actual latest 前進至 MAX 是 `LatestMismatch`。P3-D arithmetic 仍 fail fast 處理非法 `ExpectedLatest(MAX)`，但正常 commit result 不建立 `RevisionExhausted` variant。

Commit vocabulary 固定為：

```text
SkillStoreCommitResult
├─ Committed(SkillReference committed)
├─ Conflict(SkillStoreCommitConflict conflict)
├─ QuotaRejected(SkillId skillId, int current, int maximum)
├─ CapacityRejected(SkillStoreCapacityScope scope, int current, int maximum)
└─ OwnerRejected(SkillId skillId)

SkillStoreCommitConflict
├─ ExpectedAbsentButPresent(SkillId)
├─ ExpectedLatestButAbsent(SkillReference expected)
└─ LatestMismatch(SkillReference expected, SkillReference observed)
```

此 vocabulary 不重用 P3-C preparation conflict，不保存 Plan、document、definition、report、actual owner、任意 message、exception message 或 stack trace。無 `AlreadyCommitted` 或正常 commit-time `RevisionExhausted`。相同 Plan 第二次提交依 precondition 形成 `ExpectedAbsentButPresent` 或 `LatestMismatch`；不以 document equality 推斷 idempotence，不建立 attempt UUID／retry cache，也不自動 retry。Conflict 後必須重新讀 state 並重新 prepare。

## 9-D. P3-D0 sparse lifecycle、子階段與 P4 blocker

Revision lifecycle 固定為：

- New 正式 revision 從 0 開始；Existing 使用 current latest 的 `successor()`。Committed revision 不覆寫。
- retained history 可因合法 reclaim 稀疏；例如 `0, 2, 5` 表示中間 revisions 已回收，gap 不等於 corruption。
- 每個 active history 的最大 retained revision 是 implicit retention root，一般 reclaim 永不移除；因此 `max retained key` 不會倒退，也不需要 highest-allocated counter。
- active history 為空、route SkillId 與 document SkillId 不符、map key 與 document revision 不符、raw restore 重複 reference、null owner 或超過 hard ceiling 才是損壞。

P3-D 固定拆分：

```text
P3-D1：production pure-Java aggregate、owner/history truth、read API、
       detached snapshot／validated restore、hard ceilings、SkillRevision.successor()
P3-D2：SkillQuota、capacity／commit vocabulary、atomic admission／CAS／insert、
       zero-partial mutation 與正式 revision allocation
P3-D3：active pin handles、complete retention roots、latest implicit root、
       pin／unpin／reclaim 與 bounded report
```

P3-D3 不得延後到 P4。Mark roots 是每個 active history 的 implicit latest root、complete external persistent roots 與 active in-memory pins 的聯集。External roots 由 P4 composition 提供 player latest／equipped、SkillInstance、Marker、Construct 與 Schedule refs。

- owner 不 pin 全部 revisions；只有非 latest、沒有 external root 且 active pin count 為 0 的 revision 可回收。
- pin missing reference 不建立 ghost root；multiple handles 分別計數；double-close idempotent。Active pin count 不持久化，restart 後由 authoritative persistent roots 重建。
- external root snapshot 超限、截斷或不完整時 fail closed，整輪不 sweep。Reclaim report 只保存 bounded counts，不回傳 reference list；reclaim 不移除 owner binding或降低 quota count。

P3-D1～D3 第一版不實作 whole SkillId delete、retire、owner binding移除、tombstone producer或 quota release。移除玩家 Attachment latest／equipped reference不等於刪除 Store skill；owner與latest保留，quota不釋放。未來正式 retire 必須是獨立 Store operation，確認沒有 external roots／pins，並保存 persistent tombstone或等價 no-reuse truth，至少保留 highest allocated revision或永久 retired identity；是否 restore／reactivate另立 scoped amendment。

P4 開始 Java 實作前必須先完成 P4-0。Unknown／Unparsed raw preservation 目前只保證 same-family／compatible Ops round-trip；P4 不得假設 JSON-family raw 可直接無損轉成 NBT-family。P4-0 必須決定 family-tagged storage envelope與 whole snapshot／per-history／raw quarantine byte ceilings。P3-D 保存原 `SkillDocument`，不得 canonicalize或跨 family轉換 raw data。

## 10. Migration 決議

- P0～P2 尚無正式 `SkillDocument`、Appearance document 或 Draft 持久化資料，本次 schema 定案不需 migration。
- P2 `DefinitionEnvelope` 的 payload schema 語意不變。
- P3-B 才建立 skill-level 與 descriptor payload-level migration contracts；本案不實作 migration。

## 11. 相容性結論

- P0 平台、metadata、CI 與 server smoke 不受影響。
- P1 只有 `SkillRevision` 的 Java value type／Codec 與 limits 需在 P3-A 同步調整；尚無已持久化資料。
- P2 registry descriptor、`DefinitionEnvelope`、Unknown raw preservation 與 final API 繼續是穩定邊界。
- 本案不新增網路 payload、SavedData implementation、Attachment 或 runtime 真相。P3-D production pure-Java aggregate 是 Store domain truth與行為；P4 Overworld SavedData adapter才是唯一world persistence，兩者不是雙寫。
